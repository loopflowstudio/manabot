Part 1. Above the fold

Four candidate fronts. Each has a line, a sentence under it, the picture or clip, and who it is talking to. All are proposed; none exists. Numbers in the pictures are invented.

L1 · the league

Which checkpoint is better?

Etude plays your checkpoints against each other, and against opponents you choose, on machines you own or rent.

The clip: fifteen seconds. Training runs in a terminal on the left; on the right the page fills in as each checkpoint lands. The curve against the heuristic climbs and flattens. The curve against its earlier self keeps saying whether it is still improving. Then the crosstable fills, one row per checkpoint.

Who
Anyone training agents that are measured against other agents: self-play, populations, games, multi-agent teams. They have a reward curve and do not trust it.
What we would like about it
It is the differentiator you named ("comparing different checkpoints with each other in certain environments"). No tracker asks this question on its front page. The picture cannot be mistaken for W&B.
Cost
The smallest audience of the four. A single-agent RL or supervised reader sees nothing for them. The clip needs a public example game that is not Magic.

L2 · the unsatisfied

For people a little unsatisfied with W&B and SkyPilot.

One library that launches your training on rented machines, tracks it in your own bucket, and evaluates what it produced. No server. No account.

$ etude smoke ppo.py             # one tiny update and one tiny match, here, free
$ etude launch ppo.py --rent l4  # train, capped in hours and dollars
$ etude eval ppo.py              # play the matches nobody has played yet
$ etude report ppo.py --open     # the page, the same for everyone who opens it

The picture is the four commands and, beneath them, a three-column table: what you do today in W&B, in SkyPilot, in Etude. Rows are your own complaints: slow pages, one step axis, history in someone else's service, dashboards that move.

Who
The person you described: used both tools at a job, now at a small lab or alone, scraping compute together.
What we would like about it
Widest audience. The reader already knows what they would be replacing, so no concept needs teaching. It is your own sentence.
Cost
It defines Etude by two other products and invites a feature-by-feature comparison Etude loses today (no live view until EXP-57, no machine charts until EXP-58). It hides the league below the fold.

Write the loop. Etude rents the machine, and when it is taken away, rents another and carries on. It reads back as one run, inside one budget.

Part 2. The train API in EXP-56

Every design has to give a loop the same five things: where to keep files that survive the machine, how far to go, whether to stop now, a way to say "I stopped on purpose, call me again", and a way to publish a checkpoint with its clocks. The designs differ in who writes the loop's skeleton and how many of those five the author has to remember.

E1 · the handle as built in PR #103

def train(config: TrainConfig) -> None:
    with track(clocks=[Step("updates", "optimizer updates")]) as run:
        state = load(run.out) or new(config)
        target = run.until("updates", default=config.updates)
        while state.update < target and not run.stopping():
            state, metrics = one_update(state)
            run.log(metrics, updates=state.update)
            save(run.out, state)
            if state.update % 100 == 0:
                run.checkpoint(save_policy(state), updates=state.update)
        if state.update < target:
            raise Stopped("saved; call again to continue")

The loop is the author's, top to bottom; Etude answers questions. Five names to learn (out, until, stopping, Stopped, checkpoint) and three ways to get it wrong: forgetting stopping(), forgetting the final raise, and saving non-atomically. load and save are the author's; in Manabot they are 245 of self_play.py's 845 lines.

E2 · the run drives the count proposed

def train(config: TrainConfig) -> None:
    with track(clocks=[Step("updates", "optimizer updates")]) as run:
        state = run.load() or new(config)                 # the last saved state, or None
        for update in run.steps("updates", start=state.update, default=config.updates):
            state, metrics = one_update(state)
            run.log(metrics)                              # clock filled in from the step
            run.save(state)                               # atomic; this is the resume point
            if update % 100 == 0:
                run.checkpoint(save_policy(state))

run.steps yields until the target or until the run should stop; if it ends short of the target, leaving the with block raises Stopped itself. until, stopping and Stopped collapse into one line that cannot be half-written. The loop body is still the author's and still reads like CleanRL. E1's calls stay underneath for loops that do not count in one clock (two-phase recipes, the belief sampler). Cost: a second way to do the same thing; run.save needs a rule for what a state is (see S2 below).

E3 · Etude owns the loop proposed

def train(config: TrainConfig) -> None:
    loop(
        clocks=[Step("updates", "optimizer updates")],
        new=lambda: new(config),
        step=one_update,                    # state -> (state, metrics)
        until=("updates", config.updates),
        checkpoint=every(100, save_policy),
    )

The Tinker end: "just write the inner loop and we'll manage the rest", as a library call. Nothing can be forgotten, and resume is guaranteed by construction. But the author no longer has a loop to read, a recipe with two phases or an evaluation between updates has to fit callbacks, and it is the Trainer you said Etude does not sell ("I don't want to do that… not in [Etude]"). Shown so the boundary is visible, not because I think it is a candidate.

E4 · module-level, W&B-shaped proposed

import etude

def train(config: TrainConfig) -> None:
    etude.init(config=config)
    for update in range(start, config.updates):
        ...
        etude.log(metrics, step=update)
        if etude.stopping(): break
    etude.finish()

A W&B user changes one import. That is the whole appeal, and it serves the L2 front. It gives up declared clocks for a single step (your complaint about W&B), relies on hidden module state, and has no honest place for "stopped on purpose" versus "finished". Could exist later as a thin compatibility module over E1 without being the API.

A separate axis: who owns the saved state

This matters more for loop length than the choice above. Three positions, usable with E1 or E2:

What the loop writesWhat it buysWhat it costs
S1 a directory (built)save(run.out, state), its own files, its own atomic renameNo opinion about state. Any framework.Every project rewrites resume. Etude cannot tell a resume point from any other file.
S2 one named state proposedrun.save(state) / run.load(), bytes or a pathAtomic write, "resume from here" and the clock it was saved at are Etude's. Would remove part of Manabot's 245 lines; how much is not measured.One new rule: a state is whatever the author serializes; Etude never looks inside.

What I would do

Ship E1 as built with the three fixes already listed (config refusal at track(), the finished-run-marked-failed bug now on EXP-56, a local caller). Add E2's run.steps and S2's run.save/run.load on top, in the same release if they fit, since they are sugar over E1 and they are what the front page would show. Not E3. E4 only as a later compatibility shim, if L2 becomes a page. Unverified: none of E2, E3, E4, S2 or S3 has been written or run.

Three things fall out of the table.

  • E2 is the only column with no grey cell. It is best or acceptable under every front, which matters while the front is undecided.
  • L1 puts one requirement on the train API that the others do not: a checkpoint must always carry its clocks and be immutable, because a seat like Earlier(clock="updates", by=400) resolves against them. E1 already enforces this. Any state design that weakens it (S3 with rewritten checkpoints) breaks the face.
  • L2 and E4 pull together and pull away from everything else. Choosing L2 as the front is also choosing to carry a compatibility surface.

Round two: Jace as the test, and who owns the state

"In terms of E1 through E4 I definitely like E2 the best. I am somewhat intrigued by E3 but I am unsure about how flexible that would be… I don't want to go so far as to rule out innovative learning patterns like that"

What Jace's loop needs (read from RyanSaxe/jace on 2026-11-13)

One iteration of limited_iteration drafts pods, builds a deck from every pool, plays the decks, then updates five models (player, guess, deck score, deck builder, drafter) through six optimizers, one of them a shared embedding that steps with whichever model is updating. The opponent and the other draft seats can be past versions. Its docs say "This is an example loop, not a framework". It has its own 14 KB tracking.py that writes a run folder of JSON lines and checkpoints named <model>-<update>.pt, with an inputs list naming the checkpoints of other runs it started from.

Jace needsE2E3
Four phases in an order the author can changethe body of the for; untouchedall four go inside step, so Etude sees one opaque call
Five models, each with its own update countrun.log and run.checkpoint must take a model name, or a clock per modelcheckpoint=every(100, save_policy) assumes one model
Past versions as opponents and draft seats, chosen each iterationordinary code between iterations (documented reading of the population is EXP-60)needs a callback or hidden state
Skip an update on a condition (if dials.drafter_rate > 0)an ifan if inside step

E3 can run Jace only by putting the whole iteration inside step, at which point it is E2 with the for line hidden and the checkpoint rule too narrow. So E3 does not add flexibility problems so much as stop adding value once a loop is interesting. If it is still wanted for the simplest case, it can be ten lines written over E2 and shown in the docs as something to copy, not an API.

Jace also surfaces a question neither design answered: in the league a checkpoint is a player, and a Jace player is a drafter, a builder and a player model together. I have not checked whether run.checkpoint in PR #103 can record several named models at one point in a run.

State: yours, in ordinary files, described by a model

"we write code, you run it on your machine, it's saved to your machine, it's in normal-ass formats that you can read, and you own it… having a state [Pydantic] variable that makes it really clear what you get, what things we're saving, and how they relate to each other, that's all good… fundamentally, we're going to be publishing directories, checkpoints, and JSON files"

That reads as S2 with two rules added: the layout on disk is a published contract, and Etude never invents a format. A sketch, proposed:

class State(BaseModel):
    update: int = 0
    seed: int
    models: dict[str, Path] = {}      # "player" -> player.pt, written by your torch.save
    optimizers: dict[str, Path] = {}

def train(config: TrainConfig) -> None:
    with track(clocks=[Step("updates", "optimizer updates")]) as run:
        state = run.load(State) or new(config)
        for update in run.steps("updates", start=state.update, default=config.updates):
            state, metrics = one_update(state)
            run.log(metrics)
            run.save(state)
out/state/
  state.json        the model, as JSON: every field, every file by relative name
  player.pt         your bytes, in your framework's format
  player.opt.pt

Etude's part is the boring part: write the directory whole or not at all, record which clock it was saved at, carry it to the next machine. Reading it back needs json and your framework, not Etude. A checkpoint would be the same shape with fewer fields, which is the "exports look the same" you described. Unverified: how tensors get from memory to the file fields without an extra copy is not designed.
