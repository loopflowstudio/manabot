What is Etude for, and which noun sits at its centre?

The decision: Etude can be built around the run, around the player and the match, or around the question. Each is a different product with a different first page of the README, and each tells us what to spend API design on. They stack, so the real choice is which one is the headline and which are layers.

In the code below, tinted text is proposed. Everything else exists in Etude today.

Where the newer companies are heading

Tinker (Thinking Machines) gives the researcher four calls: forward_backward, optim_step, sample, save_state. The training loop, the data and the loss stay in a script on your laptop. The service owns everything about GPUs. Search results show Fireworks and Baseten now documenting similar training APIs, so this shape is spreading.

Prime Intellect makes the environment package the unit: a task set plus a scoring rubric, published to a hub, and used unchanged by evaluation and by training. Their May 2026 release gave evaluation and training one shared config shape. Hosted training takes a config; the prime command sets up a workspace built for coding agents to work in.

SF Compute Autoresearch (launched 11 September 2026, also called givemeanode) is the closest thing to direction C that is on sale. A coding agent such as Claude or Codex connects over MCP or a command line and gets a container on an H100, billed per minute, with a "research harness that executes experiments and records results". Sandboxes save disk and memory state so an RL experiment can fork from a prepared environment. Fully managed agents, "given source code, an objective and a budget", are in private preview. It is sold by a compute market, so its job is to sell GPU minutes.

Four things these companies are doing, which I read as the direction of travel:

  1. The loop goes back to the researcher. The platform shrinks to a few primitives that hide machines. Corrected by Jack Heart: Tinker "kind of is saying, 'We'll sell you a trainer class'", since the gradient step is theirs behind an API. Etude owns no part of the step and is a library: "You can just call our code." The trainer for Magic is Manabot, which is not what Etude sells.
  2. The reusable thing is the environment and its scoring, not the model code. Evaluation and training read the same definition. Extended by Jack Heart: only if the environment includes "what are the other policies that are in the situation". An experiment sets up the game (format, drafting, deck building) and "who the other players are", in a world that is "more evolutionary".
  3. The command line and docs are written for coding agents as much as for people.
  4. Experiments are getting cheap to write. Karpathy's autoresearch (March 2026) has an agent run about a hundred five-minute experiments overnight against one metric, with a text file for direction and a git log for memory. Its critics point at exactly what is missing: one number is easy to game, and a git log is a poor record of what was learned.

Where none of them is going. Tinker and Prime Intellect are for language models only and assume one policy scored by a fixed rubric. All three run on their own machines. SF Compute's harness "records results", but nothing public describes a vocabulary for what a result means, how it is checked, or how the next agent finds it. Multi-agent RL breaks the fixed-rubric assumption, and a compute seller has no reason to build a record that works on someone else's machines. Those are the two openings.

What multi-agent changes

  • A result is a relation, not a number. "Checkpoint 3200 scores 61%" means nothing without "against whom, in which seat, on which deals". W&B and ClearML have no place to put that.
  • Results go stale. A checkpoint's standing changes whenever a new opponent appears. Evaluation is never finished; it is a ledger that keeps growing and gets re-read.
  • Training reads other runs. Opponents come from a population of earlier checkpoints, sometimes from other runs. Lineage is a graph that training itself walks.
  • Players are different kinds of thing. A neural checkpoint, a scripted heuristic, a language model behind an API, a person. They need one interface.
  • Measurement quality is specific. Paired deals with seats swapped, and training seeds as the unit of evidence. These are the things Manabot protects most carefully.
  • The cost is simulation on CPUs, not GPU hours.

Softmax is the useful test of whether this generalises past card games. Their benchmark scores an agent by how much better its team does, averaged over random teammates drawn from a population. Their site now describes "a universe of multiplayer games where humans and their coding agents compete, cooperate, and interact". That is the same structure with one addition: seats belong to teams, and the score can be shared. If Etude's match has seats, optional teams and a score per seat, it covers Magic, poker, Softmax's cooperative worlds and language-model agents negotiating, without knowing what a card is.

Direction A · the noun is the run

The run contract

"Write your training loop as one file. Etude makes it survive rented machines."

Etude is to your own or rented compute what Tinker is to theirs: a handful of calls that make any loop resumable, budgeted and tracked. This is the direction MTG-329 and EXP-56 are already on, finished properly.

def train(config: Config) -> None:
    with track(clocks=CLOCKS, seed=config.seed, config=config) as run:
        state = load(run.out) or new(config)
        while state.update < run.until("updates", default=3200) and not run.stopping():
            with run.time("collection"):
                batch = collect(...)
            with run.time("learning"):
                metrics = update(...)
            run.log(metrics, updates=state.update)
            save(run.out, state)
        run.checkpoint(policy, updates=state.update)
$ etude smoke job.py              # one tiny update here, spending nothing
$ etude launch job.py --rent l4   # capped at the job's max_usd
$ etude run train:train --config '{"streams": 2}' --until updates=4

The store holds runs, rows, checkpoints, attempts.

Appeal. Small, finishable in weeks, useful to any RL or fine-tuning project. It is the honest description of what exists.

Cost and risk. Low cost. The risk is that it is a follower: W&B plus SkyPilot or Modal covers most of it, and "a nicer tracker with a launcher" is a hard thing to be known for. It also says nothing about the part of Etude nobody else has, which is evaluation between players.

Direction B · the noun is the player and the match

The league

"Experiment tracking for agents that play each other."

The population is the first-class object. Every checkpoint is a player. Every result is a match between players in seats, on named conditions. Strength is always read from the ledger of matches, so it is always current. Training draws its opponents from the same population that evaluation rates.

# What evaluation asks for. This shape exists today in experiments/elemental.py.
def eval(state: ExperimentState) -> list[Job]:
    rated = [c for run in state.runs for c in run.checkpoints]
    return [evaluation(Benchmark(name="grid", matchups=grid(rated, heuristic)), play=play)]

# What training asks for.
league = run.league()                                # every player this experiment has recorded
opponent = league.sample(by="win-rate-against-me")   # or uniform, latest, a named anchor

run.checkpoint(policy, updates=u)                    # joins the league as a player

The store holds players (checkpoints, code, hosted models), matches with seats, teams and conditions, per-seat scores, and the run records underneath.

What it implies for the API.

  • The run contract from A stays, but stays small. It is plumbing, not the product.
  • Match gains optional teams and a score per seat, so shared-reward games fit.
  • A Player is anything with act; a hosted language model is a player like any other. The types Player and Inference already exist.
  • Paired conditions (the same deal with seats swapped) become an Etude concept, not a Manabot one.
  • The report's main charts are a rating over a clock, a payoff matrix and head-to-head, which etude.report already has.

Appeal. Nobody else models this. It is where Etude's evaluation code already is, it is what Manabot needs daily, and it reaches Softmax-style cooperative research and language-model agents in games with one data model. A small field, but one where Etude can be the obvious choice.

Cost and risk. Medium cost: a league reader for training, teams in the match record, generalising paired deals. The market today is small. The bet is that multi-agent evaluation becomes ordinary as language-model agents are deployed against and alongside each other.

Direction C · the noun is the question

The lab that remembers

"State a question and a budget. Agents run the experiments. You review the findings."

This is the radical one. Experiments are becoming cheap to write, so the scarce things become: knowing what has already been tried, trusting a result, and controlling spend. Etude Cloud is a research record with a fixed vocabulary, and agents are assigned to questions inside it. The open-source SDK is how both people and agents write to that record.

# The vocabulary. Manabot's own experiment rules already describe most of it.
Question     what we want to know, the method, the known confound, a cost cap
Experiment   a file at a commit: runs(), eval(state), report()
Run, Match   what was executed, with seeds and paired conditions
Evidence     the tables those produced, immutable, addressed by digest
Finding      a claim, the evidence it cites, and who reviewed it
$ etude ask "Does learning from both seats beat one seat per learner decision?" \
      --method "matched updates, head-to-head on paired deals, 3 seeds" --max-usd 25
question q-0412 opened. Prior work found: 1 finding (seat-comparison-v1, 2026-10-23).

$ etude questions
q-0412  running    agent wrote experiments/seat_comparison_v2.py at 3f9c2a1
                   smoke passed · 3 runs launched · USD 6.10 of 25.00
q-0409  to review  finding drafted: "uniform matchups are no worse than any curriculum"
                   cites 4 runs, 11,200 matches · USD 18.40

$ etude review q-0409      # the report, the claim, the evidence it cites; accept or send back

The store holds everything in A and B, plus questions, findings and their citations, and an index an agent can search before it proposes anything.

What it implies for the open-source SDK, starting now.

  • Every command has a machine-readable output and meaningful exit codes. Agents are the main caller.
  • Spending limits are enforced by the launcher, never by the agent's good behaviour. max_usd and etude smoke already work this way.
  • Evidence cannot be rewritten after the fact. Etude's sealed blocks and digest-named files already work this way.
  • The experiment file is the unit an agent writes and a person reviews. It already is.
  • Question and Finding are record types in the SDK, stored as files, so the vocabulary is open and the cloud only adds the index, the agents and the review queue.

Appeal. It is where the puck is going, and it answers the specific weakness of autoresearch: one gameable metric and no memory. Etude's habits (seeds as evidence, paired deals, frozen commits, hard cost caps) are exactly what makes an agent's result trustworthy. And a multi-agent league is a natural target for agents, because "is this policy stronger" has a rigorous answer.

Cost and risk. High. It is a hosted service, with accounts, agents and a review product. Every large lab is building some form of automated research, and SF Compute already sells "source code, an objective and a budget" with the GPUs attached. Without B underneath it, it competes head-on as a general tool; with B, it is the automated lab for a field that has a clear ground truth.

Two versions of C, because of SF Compute. In C1, Etude runs the agents, the commands above are a managed service and SF Compute is a direct competitor with cheaper compute. In C2, Etude is the record agents write to, the agent can be anyone's: yours in a terminal, SF Compute's managed one, a lab's own. Etude supplies the vocabulary, the launch-time spending cap, the evidence that cannot be rewritten, the search over prior work and the review queue, and SF Compute becomes one more place to rent machines. C2 is much cheaper to build and is the one a compute seller will not build.

Round two · after "it should be going through Loopflow" and "not compete on compute"

Two things Etude never is

Loopflow is a meta-harness: it sits above every agent harness. Etude is the same idea one layer down: it sits above every place you can get compute.

LoopflowEtude
Sits aboveClaude Code, Codex and whatever comes nextthis laptop, SSH hosts you own, RunPod, Lium, Vast, and SF Compute as one more
Is nevera harnessa cloud, or an agent runner
Its unit of worka Task that ends in a pull requestan experiment that ends in evidence
What it keepsSessions, Tasks, Wavesruns, matches, checkpoints, machines and what they cost

So C is neither C1 nor C2 as I wrote them. Etude does steer agents, but every agent is a Loopflow Session, and Etude builds no agent runner of its own. A chat window on top talks to Loopflow.

Who this is for. Someone without a standing allocation, getting compute from several places a few dollars at a time. A company with long-term compute brings its own cloud and needs less from Etude; SF Compute sells to a wider market. The promise here is narrower: the machines you can scrape together are used well, and you never think about which one a run landed on.

What this makes more important.

  • EXP-58 is the compute-independence work, not a metrics feature: one model of a machine across every source, what it cost, what is on it, and whether another run can share it.
  • Placement becomes Etude's job: given a budget and what is free or cheap right now, choose where a run goes, and move it when a machine is lost. The run contract in A is what makes moving safe.
  • Every Etude command needs machine-readable output, because its main caller is a Loopflow Graph step.
  • Etude and Loopflow need one agreed link between a question and the Task doing the work.

Round three: what was said on 8 to 10

8. "for right now ive decided to keep the compute launching interfaces different, and its not clear that we will need agentcompute launching". Etude launches experiment compute. Where agents run is chosen through Loopflow, and may simply be your laptop.

9. "question is the key to the Etude Cloud." The Etude SDK is what is being built now. Etude Cloud is "some combination of a hosted version of the SDK as well as this additional UI and ontology around questions". That ontology already has a design in etude-studio: one node type, Inquiry, in a graph (STU-10). The Question and Finding sketch above should be read as that.

10. The flow today is the intended one: Loopflow runs agents, the agents launch things in Etude. Agents may stay on your own machine, "given some combination of Loopflow and Etude SDKs" to read and write the Cloud's questions and to launch experiments. The agent that tends a launched experiment "might be a different agent than the agent you're using to decide which experiments to launch".

What that implies for the SDK, on my reading:

  • The SDK is the only way in. A person, a local agent and the Cloud's own pages all use the same commands and records. The Cloud adds a store, sign-in and pages; it adds no second API.
  • The SDK needs a client for inquiries as well as for runs: read what is known, attach an experiment, attach a finding. With no Cloud configured these are files or simply absent, and launching still works.
  • There are two agent roles with different needs. The deciding agent reads inquiries and prior findings and writes an experiment file. The tending agent watches one launched experiment: status, logs, machine load, spend, and when to stop or continue. EXP-57 and EXP-58 are largely what the tending agent reads.
11. What does the tending agent get to do without asking?
  1. Watch and report only.
  2. Also cancel, retry and continue within the experiment's existing budget.
  3. Also change the experiment (new seeds, a config change) within budget.
12. Naming: SDK and Cloud.
  1. Keep "Etude" for both, as "Etude SDK" and "Etude Cloud".
  2. Etude is the open SDK; the hosted product gets its own name.
  3. Decide later.

Round four: match, decline, differentiate

Said, 2026-11-13: training runs are to Etude what checkpoints are to every ML operations product, "a fundamental unit" but not "what defines the product". The target user: "in a previous job I used Wandb and Sky Pilot. I would like to get to the point where I can tell people, 'Hey if you use those tools and you're a little bit unsatisfied with them, you should try using ours.'" And: "one of the biggest places we're differentiating is the focus on evals ... being able to generate evals where you're comparing different checkpoints with each other in certain environments."

The question asked was how much to implement directly and call a drop-in replacement, and where to differ completely. A proposal:

Match: the ten-minute port

Not the same API. The same habits, so someone moving a script from W&B and SkyPilot loses nothing they used daily.

Decline: say no in the README

  • A hyperparameter search service. A sweep is a list of runs in a Python file.
  • Saved, draggable dashboards. The page is report().
  • A general artifact registry and media viewer. Checkpoints and row tables only.
  • Language-model call tracing (W&B's Weave), model serving (SkyPilot's serve), Kubernetes.
  • An import shim that pretends to be the wandb module. Its single step counter is the thing declared clocks replace.
  • Selling compute.

Differentiate: what neither can do

Why W&B and SkyPilot cannot
Evaluation as its own first-class job. Checkpoints are players. Launch and tracking are one thing. A run has a budget in dollars, survives losing its machine, and reads back as one run with its cost.Each tool knows half. W&B does not know what a machine cost; SkyPilot does not know what a run is.
Train, evaluate and report in one file at one commit, with a tiny smoke of all three before spending.Their definitions live in a YAML file, a script and a web page.
Declared clocks and pages as code.The four complaints above.
Your files, no server.W&B is a hosted database.

If that holds, the README's first example is not a training loop. It is an evaluation: two checkpoints of one run, played against each other and against a fixed opponent, with the chart that comes out. Training appears second, as the thing that produced the checkpoints.

Round five: the experiment design as source

Said, 2026-11-13: "Experiments are relatively cheap to write but they can be expensive to run ... designing the experiment is kind of like the lingua franca of doing work ... you can think about experiment design as almost sort of like a coding language because it can be 'compiled' and executed by the 'agent' runtime".

Taking the analogy at its word, each part of a language toolchain has a counterpart, and most already exist:

In a languageHereExists?
SourceThe design: question, method, known confound, what is compared, cost cap, what the agent may decide aloneAs a convention. Manabot's reports open with it; etude-studio's README lists the same fields
CompilerAn agent, run by LoopflowYes
Compiled outputThe experiment file at a commit: runs(), eval(state), report()Yes
Type checketude smoke: every entry point run tiny, spending nothingYes
RuntimeThe launcher and the machines it places runs onYes
Resource limitThe experiment's budget, enforced by the launcherPer run today; per experiment is needed

Because running is the expensive part, the cheap checks carry the weight: a design should be refusable before any money is spent, for a missing comparison, no stated confound, or a cost cap its own plan cannot meet.

15. What form does the source take?
  1. Prose, with a few required headings. The agent reads it as a person would.
  2. A typed record (fields for question, arms, metric, budget) with prose inside each field.
  3. Prose now; the record is whatever the hosted product's inquiry model needs later.
