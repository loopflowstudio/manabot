Biggest mismatch: profiler attribution & diagnostic honesty in the L4 evidence

MTG-507's L4 measurement settled the root cause cleanly: w160l8's head_dim = 20 (and w288l8's 36) falls back from native float32 MHA to aten::_scaled_dot_product_attention_math under CUDA bf16 autocast, whereas 8-aligned heads (32, 40, 48) dispatch aten::_scaled_dot_product_efficient_attention.

Two mismatches in experiments/eval_precision_profile.py distort the secondary numbers drawn from those exact traces:

  1. op_bucket steals math-SDPA conversions out of attention: checking casts_and_copies before parent != "other" moves 49.96 ms of GPU time inside policy.attention (94.6% of trained-w160-bf16's GPU cast bucket) out of attention and into casts_and_copies.
  2. bf16-cached-autocast never cached weights: nesting torch_forward_context (which enters torch.inference_mode()) inside cached_context() hits PyTorch's rule that autocast weight caching is disabled outside grad mode. Both w160l8 and w384l8 traces show bit-for-bit identical cast op counts and peak CUDA memory between bf16 and bf16-cached-autocast—while bf16-linear-once actually removed >400 cast ops/call and cut w384l8 forward time by 14.6% (18.12 → 15.48 ms) and peak VRAM by 54 MiB (640.0 → 585.9 MiB) with 0.0 logit diff.

Current implementation (178a551d79)

  • op_bucket: casts_and_copies preempts policy.attention and policy.packed_gru. Report shows w160l8 delta as +36.40 ms attention, +13.30 ms casts/copies, −9.87 ms MLP.
  • bf16-cached-autocast: Stays in CLI and report as "keep autocast cache" (65.76 ms / 17.71 ms) even though profile.json proves zero weight casts were cached (1,094 vs 1,094 aten::copy_ on w384l8).
  • bf16-linear-once: Dismissed after w160l8 stays slow; its 14.6% speedup and 54 MiB VRAM reduction on w384l8 (plus GEMM kernel switch from cutlass_80_wmma_32x32 to ampere_bf16_s1688gemm_128x128) go unmentioned.
  • Capture hook: ObservePrepared leaks ObservationSelection and Spec through vector.py and eval_throughput.py into nonlocal pending.
  • Docs: docs/evaluation.md:450-456 lists tested head widths (20, 36 vs 32, 40, 48) without stating the head_dim % 8 == 0 rule.

  • op_bucket: Respect ATTENTION/GRU and parent != "other" before casts_and_copies, then recompute the bucket table offline from the retained profile.json traces: w160l8 delta becomes +48.14 ms attention (36.41 → 84.55 ms), +0.20 ms outside casts, −8.64 ms MLP.
  • Remove bf16-cached-autocast: Delete the no-op variant from eval_precision_profile.py and state in the report why PyTorch autocast does not cache weights under torch.inference_mode(); let bf16-linear-once be the sole cast-elimination measurement.
  • Report bf16-linear-once completely: Note both that it leaves w160l8 slow (math SDPA dominates) and that it cuts w384l8 forward time by 14.6% and VRAM by 54 MiB with 0.0 logit diff on L4, while noting the GEMM kernel change as the reason to defer loader adoption to a cross-GPU parity Task.

Capture boundary & caller guidance excerpts

Walking one interaction: normal, failure, recovery, and counterexamples

Normal path: capturing and auditing an L4 profile

  1. Capture: capture() runs play_pairings on 32 deals in float32. Inside observe, 1-row singles are prepared immediately while selection is live and stored under id(prepared); record pops them, runs forward, and streams (batch, singles, logits) to a temp gzip file linked atomically on completion.
  2. Replay & bucket attribution: replay() runs uninstrumented repeats through load_torch_policy + torch_forward_context, profiles 4 deterministic calls with profile_modules, and partitions trace time with parent-first op_bucket so every scoped module owns its internal casts.
  3. Caller decision: An engineer reading docs/evaluation.md#etude-agents checks head_dim % 8 == 0 and expected rows/call before picking AGENTS_BF16 vs default float32.

Failure, recovery, and counterexamples tested

  • Multi-checkpoint capture failure: Today, passing two checkpoints to capture() fires observe_prepared twice inside step_round:421 before record() runs once, crashing assert pending is None. Keying by id(prepared) and preparing singles inside observe handles multiple checkpoints and ensures ObservationSelection never survives past step_round.
  • Offline trace recomputation: Fixing op_bucket requires zero new L4 spend because the full Chrome traces live in .runs/eval-precision-profile/l4-a468879a7a/*/profile.json. Running the parent-first classifier across the four arena traces already reproduces exact totals (59.45, 100.77, 86.48, 30.40 ms/call) with attention rising from +36.40 to +48.14 ms/call on w160l8.
  • Counterexample on bf16-linear-once parity: Although max_abs_difference_from_bf16 == 0.0 on L4 for both w160l8 and w384l8, the L4 trace shows 16 attention GEMMs changed from cutlass_80_wmma_tensorop_bf16_32x32 to ampere_bf16_s1688gemm_128x128. On another GPU architecture (A40, H100) or batch size, different tile reduction order can change bf16 rounding—so shipping it inside etude-policy-bf16-auto-v1 without cross-GPU verification risks breaking compute-class identity (irreversible once scored). Deferring it to its own Task is therefore the right call.
  • Counterexample on w160 4-head / 5-head speedups: Note that GameObjectAttention sets feedforward_dim = num_heads * embedding_dim (manabot/backends/torch/policy.py:1462), so 4-head and 5-head controls also have narrower MLPs than 8-head w160l8. The report correctly compares their bf16/float32 ratios (within each fixed model) rather than raw milliseconds across head counts, so the MLP-width difference does not confound the SDPA backend proof.
