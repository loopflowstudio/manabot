Biggest mismatch: width threshold vs head_dim % 8 SDPA fallback

The plan frames MTG-507 around two hypotheses—host-side autocast cast overhead (~1,300 ops/call) and batch/width scaling—while noting that a fixed per-call cast cost cannot explain why w160l8 adds 27.5 ms/call when w384l8 takes only 18.6 ms/call in total (scratch/plan.md:33-35). It misses the third mechanism already visible in this repository's own L4 precision report:

On the same NVIDIA L4 and PyTorch 2.15.0+cu132 stack, w160l8 padded bf16 was already 1.55× slower at 64–256 rows/call and doubled learner peak VRAM from 5.3 GB to 10.7 GB, whereas w256l8 and w384l8 sped up 1.95–2.71× and cut peak VRAM nearly in half. Why does bf16 double memory only at w160l8? Look at GameObjectAttention:

model("w160l8") uses num_attention_heads = 8, giving head_dim = 20 (20 % 8 == 4). In experiments/eval_throughput.py:90, varying only hidden_dim across (160, 256, 384) produces head_dim = (20, 32, 48). On CUDA, PyTorch's mem_efficient SDPA supports head_dim % 4 == 0 in float32, while both flash and mem_efficient require head_dim % 8 == 0 in bfloat16. When head_dim = 20 enters bf16 autocast, SDPA falls back to the math backend, materializing the full [B, 8, N, N] attention score matrix across all 8 layers (which scales with batch size B, explaining why 18.6 rows/call adds 27.5 ms and 256 rows/call adds 255 ms + 5.4 GB VRAM). Because a naive op-name classifier puts math SDPA's aten::bmm and aten::_softmax into linear/MLP or unattributed, the plan's proposed buckets can also misattribute the slowdown unless SDPA backends and peak CUDA memory are recorded explicitly.

Two concrete code boundaries in the plan also fail on contact with the existing implementation:

Current plan (73be5ae6e8)

  • Threshold grid: 8-head widths (160, 256, 384) → head_dim = (20, 32, 48), confounding width with head_dim % 8.
  • Batch capture & replay: Captures multi-row w160l8 Prepared batches, then expects w256l8/w384l8 to replay them (rejected by Prepared.binding) and re-chunks them to 1, 4, 16, 64 rows (no split exists in batching.py).
  • Candidate fix: bf16-cast-once casts all non-GRU weights to bf16, which rounds LayerNorm, Embedding, and cache_programs() away from etude-policy-bf16-auto-v1.
  • Profiler buckets: Single attention bucket; no SDPA kernel dispatch breakdown or peak CUDA VRAM.
  • Rental order: 12 full 32-deal arena repeats (~30 min) bundled ahead of / alongside diagnosis.

Recommended design

  • Deconfounded grid: Add one 8-aligned narrow point (w160 with 5 heads, head_dim = 32, or w192l8, head_dim = 24) and one unaligned wide point (w288l8, head_dim = 36).
  • No split_prepared & clean cross-width replay: Keep multi-row arena batches for exact arena replay on the capturing checkpoint; capture single-row Prepared batches for the grid and build 1, 4, 16, 64-row calls with existing batching.concatenate. For cross-width replay on identical boards, assert equal space.config, readings, and decision_memory and explicitly re-tag Prepared.binding in the harness (or prepare per width from captured raw observations).
  • Exact autocast-preserving variants: Test (a) bf16-cached-autocast (keeping PyTorch's torch.autocast(..., cache_enabled=True) open across calls—zero parameter mutation) and (b) bf16-linear-once (casting only nn.Linear and nn.MultiheadAttention projection weights/biases after cache_programs(), leaving LayerNorm, Embedding, nn.GRU, and bare nn.Parameters float32).
  • SDPA + memory attribution: Record dispatched SDPA kernels (flash vs mem_efficient vs math / bmm+softmax inside attention via record_function scopes) and torch.cuda.max_memory_allocated() per replay.
  • Diagnose first, replicate second: Run the ~3-minute replay/profile pass first on L4, then run only the arena repeats needed to measure spread and verify any bit-identical fix.

Walking one interaction: normal, failure, recovery, and counterexamples

Normal path (revised)

  1. Capture (local or L4, float32): Run 32 held-out deals once per model to save exact arena multi-row Prepared calls (for arena-order replay) plus a pool of 1-row Prepared inputs from the trained w160l8 games (composed into 1, 4, 16, 64-row batches with batching.concatenate).
  2. Diagnose on L4 (~3 min): Replay the captured sets through float32, tf32, bf16, bf16-cached-autocast, and bf16-linear-once on trained w160l8, seeded w160l8, w160 (5 heads, head_dim = 32), w256l8, w288l8 (head_dim = 36), and w384l8. Record per-call stage times, bucket totals (including record_function-scoped attention with SDPA kernel names), peak CUDA VRAM, and max/exact logit diff vs shipped bf16.
  3. Confirm in arena: If a bit-identical fix removes the penalty, apply it in agent_loader.py and run alternating arena replicates before/after; otherwise run the arena replicates to report the real spread and document the exact L4 rule in docs/evaluation.md#etude-agents (for example, requiring both head_dim % 8 == 0 and sufficient width/batch).

Where the current plan fails

  • Cross-width binding failure: replay --checkpoint seeded-w384.safetensors --batches trained-w160.batches raises ValueError("observation was admitted for a different policy configuration") at manabot/backends/torch/policy.py:771 because admission.binding() hashes hidden_dim.
  • Re-chunking gap: Slicing a 24-row Prepared batch down to 4 rows has no helper in manabot/policy/batching.py; naive slicing corrupts flat link_targets, legal_batches, facts.programs, effects, and memory schedules.
  • False parity rejection: Casting all non-GRU weights to bf16 changes LayerNorm and token_embedding, altering cache_programs() outputs and failing bit-exactness against etude-policy-bf16-auto-v1 even if eliminating repeated Linear casts would have been bit-identical.
  • Misleading docs rule: Publishing "use bf16 above width 256" when the cliff is head_dim % 8 == 0 misleads anyone evaluating w288l8 (head_dim = 36) or w192l8 (head_dim = 24).

What must survive vs what changes on purpose

  • Must survive: float32 remains the evaluation default; etude-policy-bf16-auto-v1 logits stay bit-identical if any loader fix lands; manabot.eval.agents and manabot.eval.vector stay Torch-free on import; production ActorCritic.forward_distribution keeps strict Prepared.binding checks; eval_throughput keeps its summary.json schema and does no per-call disk flushes inside timed forwards.
  • Changes on purpose: Adding head_dim % 8 deconfounding points, 1-row grid capture via concatenate, record_function-scoped SDPA + VRAM reporting, autocast-exact cast-once variants, and profiling before the 12-arm arena sweep.

Counterexamples tested

  • What if head_dim % 8 is not the cause on PyTorch 2.15 + L4? Including w160 with 5 heads (head_dim = 32) and w288l8 (head_dim = 36) costs <60 seconds of L4 replay time and immediately falsifies the hypothesis if w160 (head_dim = 32) still slows down and w288l8 speeds up.
  • What if bf16-cached-autocast is bit-identical and fast, or what if torch.autocast only caches per-enter? Measuring both persistent autocast (keeping the context alive across calls on the loader's single inference thread) and Linear/MHA-only bf16 weights tests the exact mechanism with zero guesswork—while remembering that a persistent thread-local autocast context would leak into other Torch work on the same thread if not scoped carefully, so Linear/MHA-only weights are safer for production if bit-identical.
  • What if the slowdown is driven by trained games having denser boards / more packed-GRU facts rather than head_dim? Keeping the trained-vs-seeded w160l8 batch cross plus explicit record_function buckets for packed_gru, attention_sdpa, and autocast_casts separates board density from kernel dispatch in one pass.

Findings

Scope: This work (revise plan before Pass 1). experiments/reports/cuda_precision.md already shows w160l8 padded bf16 slowing 1.55× and doubling learner VRAM (5.3 → 10.7 GB) on an L4, pointing squarely at head_dim = 20 failing CUDA's 8-element bf16 SDPA alignment. Add an 8-aligned narrow checkpoint (w160 with 5 heads → head_dim = 32, or w192l8 → head_dim = 24) and an unaligned wide checkpoint (w288l8 → head_dim = 36) to the grid, scope GameObjectAttention / packed_gru / transfers with torch.profiler.record_function in the profiler pass so math SDPA's aten::bmm + aten::_softmax do not hide inside linear/MLP, and record dispatched SDPA op names and torch.cuda.max_memory_allocated().

Scope: This work (revise plan before Pass 1). Prepared.binding hashes ModelConfig (hidden_dim, num_attention_heads), so the plan's threshold grid cannot replay w160l8-prepared batches on w256l8 or w384l8 as written, and manabot/policy/batching.py has no split to re-chunk multi-row batches to 1, 4, or 16 rows. Keep multi-row arena batches for exact same-model replay, capture single-row Prepared batches for the grid (building 1, 4, 16, 64 via existing concatenate), and either prepare grid rows per target config or re-tag Prepared.binding inside the harness only after asserting identical space.config, readings, and decision_memory.

Scope: This work (revise plan before Pass 1).
