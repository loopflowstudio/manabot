The biggest mismatch: managym/replay.py still treats isolated vector step failures like strict batch exceptions

Pass 5 unified isolated reset and step failures under one per-game GameFailure(operation, error_class, traceback) record so that RecordedVectorEnv, _GameJournal, GameRecord.for_game(), and managym.replay:main all know which exact slot failed natively and why. Walk two concrete counterexamples reproduced directly on HEAD (e9e5440e8a):

  1. Counterexample 1 — detached or journaled isolated step failure reports original_outcome: "execution_outcome_unknown": A 2-slot RecordedVectorEnv runs step_isolated_into_buffers([0, 999_999]). Slot 1 fails natively and records GameEnd(status="failed", failure=GameFailure(operation="step", ...)). Detaching slot 1 with detached = vector.take_slot_record(1) produces a single-game record with detached.execution_outcome == "failed" and detached.games[0].end.status == "failed". Yet calling replay_failure_inputs(detached) (or replaying the journaled slot 1, or calling manabot.sim.replay on the retained evaluation record) executes managym/replay.py:579-583:
    • evidence.mode == "vector" is True and failed_opening is False (because operation == "step", not "reset").
    • So ReplayAgreement overwrites evidence.execution_outcome ("failed") with "execution_outcome_unknown"!
    • An isolated reset failure from the exact same GameFailure path reports "failed". The comment on line 577 explicitly scopes "execution_outcome_unknown" to a strict vector exception (where game.end is None and no slot outcome was observed); an isolated step failure carries game.end.status == "failed" and proved that exact stream failed.
  2. Counterexample 2 — boundaryless vector.snapshot() marks healthy sibling slots as at_retained_failure: True (and fails on detached empty slots): On the same 2-slot RecordedVectorEnv with no journal_path (snapshot.boundary is None), calling replay_failure_inputs(vector.snapshot()) hits lines 469–473 and dispatches both slot 0 (healthy, committed == 1 == len(actions), game.failure is None) and slot 1 (failed) directly to _replay_game_inputs:

Findings

What breaks:

  • In managym/replay.py:579-583, _replay_game_inputs checks evidence.mode == "vector" and not failed_opening. Replaying an isolated vector step failure — via replay_failure_inputs on vector.snapshot(), take_slot_record(), games_path, a journal, or manabot.sim.replay — reports original_outcome: "execution_outcome_unknown" even though game.end.status == "failed" and evidence.execution_outcome == "failed" proved that exact stream failed (whereas an isolated reset failure reports "failed").
  • In managym/replay.py:468-473, replay_failure_inputs sends every stream of a boundary is None snapshot straight to _replay_game_inputs. When a boundaryless vector.snapshot() carries a per-slot GameFailure, healthy sibling slots report at_retained_failure: True (contradicting the journaled ready path's False), and a detached empty sibling slot (players == [] after take_slot_record) raises ValueError in game.setup() instead of returning status: "setup_unavailable".

Fix: In _replay_game_inputs, treat any stream with an observed isolated failure (game.end is not None and game.end.status == "failed") like scalar and failed-opening records so original_outcome preserves evidence.execution_outcome ("failed") while strict vector batch exceptions (game.end is None) keep "execution_outcome_unknown". In replay_failure_inputs, handle non-failing sibling streams of a boundaryless per-slot-failure snapshot consistently with the boundary.phase == "ready" branch (at_retained_failure=False, matches_binding=None, matches_error=None, and status="setup_unavailable" when not game.players). Assert both original_outcome == "failed" for isolated step failures and not healthy["at_retained_failure"] for boundaryless snapshots in tests/env/test_record_reducers.py and tests/eval/test_vector_eval.py.
