Concept Review: Policy-Input Vocabulary Surfaces (MTG-504)

Area reviewed: Policy-input vocabulary surfaces across managym and manabot — how the engine publishes printed definition tokens (catalog_tokens), hashed record names (record_vocabulary), runtime-only program tokens (runtime_tokens), decision-memory labels, and historical renames/retirements (token_renames.rs), and how manabot builds embedding tables (catalog.py), admits live observations (admission.py, decision_memory.py), binds pre-0.3.0 checkpoints (binding.py), and traces historical writer hashes (scripts/pinned_pilot.py / scripts/pilot_names.rs).

Why this area: HEAD (65d60f78b6, based on origin/main 6a131c4dc9, awaiting PR #636 / MTG-501) contains only the pre-implementation plan in scratch/plan.md and scratch/questions.md. Splitting record_vocabulary() touches the entire loop from native registration through policy table construction, live admission, checkpoint rebinding, and historical hash debugging. Reviewing the whole loop before Pass 1 catches three concrete correctness traps in the plan and sharpens the public surface.

Biggest mismatch: generating historical retirements from live mutable vocabularies

Walk one concrete lifecycle through token_renames.rs and manabot/policy/binding.py::bind_catalog: a checkpoint saved on 0.2.6 is loaded on 0.3.0, and then loaded again on 0.3.1 after a newly authored card prints a previously runtime-only symbol.

First, check what already sits in managym/src/cards/token_renames.rs today. Before PR #636, token_renames.rs's unit test checked TOKENS successors only against printed catalog_tokens(), so the author of the kept permanent rename put None in TOKENS and carried the actual rename on the synthetic RECORDS row:

Now trace the three counterexamples that break the plan's generator:

  1. Silent vector loss on pre-rename checkpoints. Deleting RECORDS's two Some("execution/6/…") entries and retiring them while leaving TOKENS at (Text, "kept creature", None) and (Text, "creatures each player sacrifices", None) drops the rename from both families. On checkpoints predating that rename, kept permanent and permanents each player sacrifices silently become unseen (mean-initialized) instead of inheriting the trained vectors. PR #636 already switched the token_renames.rs unit test to PROGRAM_VOCABULARY, so both successors can now move directly onto TOKENS where they belong.
  2. Graduating a runtime token into a printed card breaks every 0.2.x checkpoint. Look at record_vocabulary.rs lines 212–222 (and PR #636's LoyaltyCost::MinusX and TriggerCondition::TappedForMana): those symbols live in execution_names only because no printed card uses them yet. When a future card prints TargetSpec::Ability or LoyaltyCost::MinusX, an author removing it from runtime_tokens() will not add it to TOKENS (the token is still live in catalog_tokens()). Because CatalogTokens stores 32-bit hashes, not name strings, nothing can re-hash "execution/3/TargetSpec::Ability" once it leaves runtime_tokens(). Every 0.2.x checkpoint immediately fails bind_catalog with ValueError: unexplained record_name key.
  3. Editing decision_memory::RECORD_NAMES corrupts historical retirements. Generating (Variant, "DecisionMemory::<name>", None) from live RECORD_NAMES invents bogus retirements for future 0.4.0 labels and silently drops pre-0.3.0 retirements if any of the 44 existing labels (roughly 16 of which are unused field/context names like Life or BoardCounts) are ever cleaned up.

Counterexample tested and rejected for binding.py: could bind_catalog skip missing record_name keys whenever their old embedding row was already bound by a record_token? No. Real aliased record names (like flying ↔ Keyword::flying) share a row with their token too; skipping them would silently swallow an accidental deletion of a live record name instead of failing loudly. Explicit hash classification in token_renames.rs is the right mechanism — it just must be fed by a frozen pre-0.3.0 snapshot, not live mutable lists.

Planned: live lists synthesize historical retirements

  • RECORDS retirements generated from live runtime_tokens() ∪ TOKENS.
  • TOKENS phantom retirements generated from live decision_memory::RECORD_NAMES.
  • kept creature & creatures each player sacrifices left as None in TOKENS while their Some(…) renames are deleted from RECORDS.
  • Deleting TargetSpec::Ability from runtime_tokens() after a card prints it breaks every 0.2.x checkpoint.

Recommended: frozen pre-0.3.0 ledger in token_renames.rs

  • Move Some("kept permanent") and Some("permanents each player sacrifices") onto TOKENS so pre-rename vectors stay preserved.
  • Freeze the 44 pre-0.3.0 DecisionMemory::* names in const LEGACY_DECISION_MEMORY_TOKENS inside token_renames.rs (append-only history, independent of future RECORD_NAMES edits).
  • Freeze the ~130 manual pre-0.3.0 runtime symbols (structs, enums, fields, EXECUTION_TEXT at the 0.3.0 cut) in const LEGACY_EXECUTION_TOKENS; expand execution/6/<name> dynamically only from the append-only content pack (card/set/play-grant names) plus TOKENS old names.
  • Graduating a symbol from runtime_tokens() to a printed card never invalidates a 0.2.x checkpoint.

Second mismatch: three lists to compute one program-token vocabulary

Issue #629 happened because callers saw managym.catalog_tokens() and assumed it was the complete program-token vocabulary. Under scratch/plan.md, a caller sees two token functions — catalog_tokens() and runtime_tokens() — and still gets the wrong answer if they compute printed | runtime, because record_vocabulary() secretly owns a third slice of unprinted program tokens (every Modification::* variant, plus any unprinted Keyword::*, CounterKind::*, SourceQuality::*, or subtype):

In PR #636, Modification::AddTypes is registered only as a RecordName token in record_names() while its closing token /Modification::AddTypes is registered in execution_names(). Keeping that split forces docs/engine.md, PROGRAM_VOCABULARY, test_effect_vocabulary.py, and test_pooled_mana_classes_input.py to maintain a 3-way union of three different return shapes.

Planned: 3-way union; record_vocabulary() still appends tokens

printed = set(zip(cat["token_kind"], cat["token_value"]))
rec_tok = {(k, v) for _, _, _, k, v in managym.record_vocabulary() if k is not None}
runtime = {(k, v) for k, _, v in managym.runtime_tokens()}
admitted = printed | rec_tok | runtime

Modification::AddTypes is in rec_tok; /Modification::AddTypes is in runtime.

Recommended: 2-way union; record_vocabulary() tokens are pure aliases

printed = set(zip(cat["token_kind"], cat["token_value"]))
runtime = {(k, v) for k, _, v in managym.runtime_tokens()}
admitted = printed | runtime

runtime_tokens() includes every non-printed (or runtime-registered) program token, including record-aliased ones. In catalog.py, runtime_tokens() appends rows first; then every non-None token in record_vocabulary() strictly aliases an existing entry in tokens (asserted, never secretly appended).

Third mismatch: scripts/pilot_names.rs breaks historical key lookup

scripts/pinned_pilot.py names --at <rev> extracts an archived historical commit of managym, copies HEAD's scripts/pilot_names.rs into it, and compiles it against that old crate:

Plan Pass 2 updates scripts/pilot_names.rs to call runtime_tokens() and decision-memory names. Doing so unconditionally will fail to compile against every pre-0.3.0 commit (such as ab2b757d9 in docs/observation-and-model.md), breaking the exact debugging tool used to classify unexplained keys from older checkpoints. Instead, scripts/pinned_pilot.py::names_at should detect whether the archived record_vocabulary.rs defines pub fn runtime_tokens (mirroring its existing inspection of tokens.rs) and emit the matching probe for pre-0.3.0 vs. post-0.3.0 writers.

Fourth mismatch: decision-memory vocabulary placement and missed test

Every other engine vocabulary lives at the top level of managym and is tracked in managym/__init__.pyi and tests/public_api.json. The plan places decision-memory names at managym.decision_memory.decision_names() "from a native read" without naming the PyO3 binding, even though managym/__init__.py re-exports every non-underscored symbol from _managym via from ._managym import *. Meanwhile, tests/model/test_record_vocabulary.py:104 asserts that record_name_keys length equals len(managym.record_vocabulary()) with decision_memory=True and is missing from the plan's consumer list:

Exposing one top-level native function (e.g. managym.decision_memory_names() or managym.decision_memory_vocabulary()) in managym/__init__.pyi keeps all engine vocabularies on one contract-checked surface and lets managym.decision_memory.decision_name_values() derive directly from it without a hidden _managym trampoline.

Findings

This work (Pass 1). Move the two live renames from token_renames::RECORDS onto token_renames::TOKENS ((Text, "kept creature", Some("kept permanent")) and (Text, "creatures each player sacrifices", Some("permanents each player sacrifices"))), which PR #636's PROGRAM_VOCABULARY check now accepts. Without this, removing the execution/6/… rename rows silently turns both into retirements and mean-initializes both vectors on pre-rename checkpoints.

This work (Pass 1). Do not generate historical retirements from live mutable runtime_tokens() or decision_memory::RECORD_NAMES. Freeze the ~130 manual pre-0.3.0 runtime symbols and the 44 pre-0.3.0 DecisionMemory::* names as static historical constants in token_renames.rs, expanding only pack-derived card/set/grant execution/6/<name> entries (plus TOKENS old names) dynamically. Add a unit test verifying that removing a runtime token or memory label does not drop its historical retirement, plus a constructed pre-0.3.0 decision-memory checkpoint binding test in tests/model/test_checkpoint_binding.py.

This work (Pass 1 & Pass 2). Include all non-printed program tokens (including tokens aliased by record_names() such as Modification::* and unprinted Keyword::*/CounterKind::*/SourceQuality::*/subtypes) in runtime_tokens(). Then catalog_tokens() ∪ runtime_tokens() is the exact admitted program-token vocabulary (2 lists, not 3), and record_vocabulary()'s token column is strictly an alias into that vocabulary (asserted in catalog.py).

This work (Pass 2). Do not add post-0.3.0 imports unconditionally to scripts/pilot_names.rs. Have scripts/pinned_pilot.py::names_at detect whether the archived crate defines runtime_tokens (and memory names) and compile the matching probe so historical key debugging works across the 0.3.0 boundary.

This work (Pass 1 & Pass 2). Publish the native decision-memory label list directly in managym/__init__.pyi and tests/public_api.json alongside record_vocabulary() and runtime_tokens() (returning (namespace, name, value) or (name, value)), and derive managym.decision_memory.decision_name_values() from it. Update tests/model/test_record_vocabulary.py:104 (missed in the plan) to account for the 44 memory rows when decision_memory=True, and replace magic namespace literal 1 in manabot/policy/decision_memory.py with RecordNamespace.TOKEN.

This work (Pass 1, small cleanup). Both record_names() and execution_names() currently serialize every ObjectDefinition in the pack with serde_json::to_value(definition). Keeping a shared pack walk (or avoiding redundant serialization) avoids doubling startup work when catalog.py calls both functions.
