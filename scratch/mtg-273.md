# MTG-273 — self-play collection slowdown

## Outcome

The Task requires “The specific cause, backed by evidence from a profile or a
controlled reproduction, and a fix with a check that time and memory per update
stay flat over a long run.” The implemented repair removes one reproduced
matchup-metric indexing cost; full causal attribution and long-run acceptance
remain open. Preserve completed-game deck/opponent/position/count evidence,
policies, sampling, recovery allowance, frozen configurations and run evidence.

## Implemented approach

- Removed live `self_play_outcomes` lists from UpdateDiagnostics and their
  flattening in the executor, including the live writer's deck-hash metric names.
- `outcome_tables.write_outcomes` seals digest-named JSON under the metric run's
  `artifacts/self-play-outcomes/`, using `.partial`, fsync and atomic rename.
  `execution._execute_regime` logs its digest with the ordinary update clocks.
- `update_metrics._updates` decodes one block at a time, replaces duplicate rows
  by update, and applies resume cutoffs in chronological attempt order, including
  empty resumed attempts. It then reads selected tables through each block's
  Storage and run prefix. Missing/corrupt selected evidence fails visibly.
- Removed cached whole-block history and all-attempt row lists. The offline
  projection still retains selected history and expands matchup counts; this
  is not a constant-memory report reader.
- Preserve SelfPlayCounter and snapshot semantics, exact counts, ordinary
  update clocks, all stored historical metric bytes and report behavior.
- Retain keyed-list flattening for historical StageRecord diagnostics and the
  offline table projection; this is reader compatibility, not a live writer.

## Concept review — 2026-11-11

Outcome for loop-or-next: **nothing to change and no open product choice**.
Advance this review; do not interpret it as full Task acceptance. The existing
design already separates a sound evidence representation from the missing
causal and long-run performance proof. Execution placement/bounds remain the
later demo decision described above, not a new product-model question here.

The experience stays: train, retain/copy the whole metric run, and inspect the
same per-update matchup counts. One completed game's two seat outcomes belong
to an update's evidence. The digest identifies immutable content; the selected
metric row identifies which attempt/update owns that content. These are useful
distinct responsibilities, not two independently managed result lifecycles.
Do not introduce a table registry, a second uploader, a checkpoint dependency,
or a live scalar compatibility writer. Existing `docs/training.md` monitoring
guidance and `AGENTS.md` training-record instructions express this interaction;
leave them unchanged. No unbuilt usage or skill behavior is proposed.

Concrete review example (illustrative, not an executed game): A defeats B on
the play at update 12. Its table contains A/B/play wins=1 and B/A/draw losses=1.
After shipment and relocation, `read_updates` exposes those same counts. If
the table seals but logging fails, that orphan supplies no result. A later
attempt resumed at update 11 removes the old update-12 reference before any
table read, including when the new attempt logs nothing. A replacement update
12 supplies its own reference. Identical table contents may share a digest
across updates without merging the updates.

Counterexamples to preserve: scanning every table resurrects superseded counts;
reading references before selection fails on missing superseded evidence;
copying only metrics leaves selected evidence unavailable. The implemented
selection and shipment model addresses these cases. A missing/corrupt selected
table must remain an error, never an inferred zero. A failed seal propagates;
this design adds no automatic retry of an already-advanced learner and makes no
new crash-recovery guarantee. Existing committed-state recovery remains owner.

Next show the integrated checks and the remaining causal/long-run evidence in
the acceptance section. Keep Python allocation, process RSS and device memory
separate; do not turn the 44-fold fixture allocation reduction into a training
speedup or flat-history claim. Review page: `scratch/concept-review.html`.
