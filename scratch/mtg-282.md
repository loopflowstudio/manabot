# Deck-building foundations

Deliver all four outcomes in MTG-282, following `docs/deck-building.md`:
a published, loadable 922-event pool corpus with a frozen split; native
Limited rules and Python picking; public game rows without recovery enabled;
and an executable typed module stage in a two-model regime.
No training experiment, new learner, world change, or existing-stage move.

## Preserved boundaries

Limited rules, tests and bindings now use `format::limited`; there is no
`cards::limited` compatibility surface. Pool derivation admits entries and
records unknown-card exclusions; malformed lists still fail derivation.
Existing private game attempts remain recovery evidence; aggregate counters
remain summaries. Frozen single-agent
recipes and historical trophy corpora keep their serialized meaning.

## Current implementation (post-review direction, 2026-11-11)

- Native `managym/src/format/limited.rs`: `CardPool` (names/counts, admitted at
  construction), `Limited` (rules only), stateless `Limited::selection(pool,
  deck, max_cards)`, `Limited::issues`, and `LimitedBuild` (commits selections).
  Python: `managym.CardPool`, native submodule `managym.format` (`Limited`,
  `LimitedBuild`; stub `manabot/managym/format.pyi`). `LimitedRules`,
  `LimitedChoices` and `choices`/`picks` are gone, not aliased.
- `manabot/pools.py`: plain `PoolCorpus`/`Pool`/`PoolProvenance`, schema 2, no
  engine/training import. Provenance records `basic_lands` (used by the
  human-build check) and `human_build_indexes`. `experiments/tla_pools.py`
  keeps all 1,000 drafts with names as recorded; only unknown-name admission
  failures are tolerated.
- `manabot/game_results.py`: `GameSeat{pool, build}`, `CompletedGame` (no
  `on_play`), `read_game_results`. The writer is
  `manabot/training/result_journal.py`.
- `UniformDecks.pools`/`builds` replace `build_episodes`. With no `entry_ids`,
  pooled players are named `pool` or `pool/build`; the collector joins seats
  through `UniformDecks.seats_by_player()`.
- `Stage.trains` is a tuple. Module stages export each trained model as
  `raw/<name>`; self-play keeps `raw`. `run.selected_models` maps names.

`LimitedChoices`, `build_episodes`, `GameSeat.entry_id`, `on_play`,

## Concept review — 2026-11-11

Outcome for loop-or-next: nothing to change and no open product choice; advance.
Keep the experience in `docs/deck-building.md`: restore a frozen population,
ask the native rules for the next pick or stop, join completed games to both
entries and optional build episodes, and execute stages with explicit model
roles. The review page is `scratch/concept-review.html`. No runtime code or
public contract changed in this review.

The biggest conceptual trap is treating an outcome as an optimizer sample or
a recovery attempt. Preserve one row per completed native game even when both
seats learn or a later update fails. Stage/attempt scope must accompany its
stream/game ordinals; replayed attempts cannot be concatenated as independent
games. A result is retained evidence, not permission to resume a named-model
run. The normal path, optimizer-exception path and existing restore guidance
fit that distinction; abrupt process death is not the same as handled failure
and does not promise an automatically sealed journal.

Counterexamples retained for the next review: identical decks from two events
must remain two pool comparisons; a 41-card reference must not become a
40-card list; a legal 61-card deck may exceed a 60-pick episode; adding the TLE
exclusions must not move existing split assignments; mutating a frozen module
reader must not mutate its run-owned model. These require the current distinct
identities and authorities, rather than another shared lifecycle. The next
evidence is the outstanding gate validation above, not a builder training run
or a migration of existing stages. No games, training or test suites were run
for this conceptual review; earlier receipts remain earlier receipts.

### Third pass: names — 2026-11-11

Jack Heart, on the review's wording: "why are we calling cards events?"
"Event" is 17Lands' `draft_id` (one player's draft and its games). The corpus
exposes three ids for two things: `event_id` and `entry_id` are 1:1 in all 922
entries (`entry_id` = `TLA:PremierDraft:<event>:<seventh-win build index>`),
plus `build_episode`. managym already uses "event" for in-game events. The
doc uses "event" 19 times and four spellings for the human's deck
("reference", "reference build", "human reference", "human reference deck").
Proposed, open (question 6): the vocabulary is pool and build; the 17Lands
draft id is the pool's id; `entry_id` and "event" leave the public surface.

Jack Heart, on the doc's opening example: "rules = managym.LimitedRules(pool={"Llanowar Elves": 6})
choices = rules.choices(picks={"Llanowar Elves": 6, "Forest": 33}) This doesnt read naturally to me".
Proposed, open (question 7): the format is `managym.Limited`, taking the pool
and the deck as arguments (`next(pool, deck)` -> `cards`, `can_stop`;
`issues(pool, deck)`); "picks" becomes "deck".

Jack Heart, on the picking call: "managym.CardPool?" then "card_pool.select card?"
Proposed, open (question 7): the pool is the object and cards are selected
from it. Open sub-choice: `select` on the pool itself, or on a build the pool
starts. jace already has a `CardPool` (the whole card universe, defining card
ids), and managym has `world_pool`/`content_pool` for the world's cards.

Jack Heart: "i feel like the rules and the specific cards available shoudl be distinct".
Proposed, open (question 7): `CardPool` holds only the cards available;
`Limited` holds only the rules; a build is started from both and cards are
selected into it. This is the same split as jace's `BuildRules` and `Pool`.

Jack Heart: "managym.format.Limited()?" Proposed, open: rules live under
`managym.format` (mirroring `managym/src/format/`); `CardPool` stays top-level.

Jack Heart: "why do we need to tie the corpus to the engine at all". Nothing
found that requires it: the engine rejects unplayable decks at game start,
regimes embed the deck lists a run used, and 17Lands names equal engine names
in the 922 admitted pools. Proposed, open (question 1a, sharpened): the corpus
is plain source data with no engine import or world field; a caller filters
playable pools with the engine's existing unsupported-card check.
