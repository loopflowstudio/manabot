# MTG-290 plan

## Outcome and constraints

An outside engine consumer can interpret every supported observation layout by
name and value semantics, discover a recommended input version, and recover from
an older version's representability rejection without changing saved inputs.

The task brief's acceptance is: "the layout is readable from Python for every
supported version with a test tying it to the native encoder widths; jace's
column-24 lookup could be replaced by a name; and the version guidance and
improved error are in place."

`src/jace/engine/manabot.py`, and hard-codes `_PERMANENT_DEFINITION_COLUMN = 24`.
Its adapter and `docs/status.md` / `docs/getting-started/install.md` motivated
named metadata and guidance beyond the v6 default. No downstream jace change

Frozen versions, array values/capacities, checkpoint identities and worlds stay
unchanged. The task title's "accepts every legal board" is broader than the
implemented finite-capacity contract: a newer vocabulary does not remove row
limits. The brief's quoted acceptance is covered, but literal acceptance of
every legal board is not established. Capacity failures remain explicit; no

scope remain visible for demo in `scratch/questions.md`.

## Implemented approach

- `managym/src/agent/observation_layout.rs` owns named columns, indices, widths
  and `ValueLayout` semantics for inputs 1–9 and both event projections.
  Native encoder writes and the observability guard use those names; numeric
  ABI assertions and independent Python parity remain. Existing public Rust
  index constants refer to this authority. No deletion targets remain.
- `managym/src/python/layout_bindings.rs` publishes `observation_layout` and
  `recommended_policy_input_version`, with typed dictionaries in
  `manabot/managym/__init__.pyi`. Fixed extents and caller capacities are
  distinguished; discovery requires neither a game nor Torch.
- `RECOMMENDED_POLICY_INPUT_VERSION` is 9. In
  `observation_encoder.rs`, both `UnsupportedLayerInput` and
  `UnsupportedEffectExecutionInput` name the selected version, v8 as the
  minimum supporting vocabulary, and v9 as the new-consumer recommendation.
  Implicit fresh v6 and omitted-checkpoint v1 behavior remain unchanged.
- `docs/observation-and-model.md` supplies named-column examples and one
  version/recovery section, linked from `docs/engine.md`. V9 adds naming
  identity to v8's layer/execution programs; it is not an unlimited-capacity
  guarantee or permission to reinterpret a checkpoint.

## Concept review (2026-11-11, headless)

A consumer learns three things: arrays have named columns
(`observation_layout(version)`), new work pins an explicit version
(`recommended_policy_input_version()`), and a rejection names the version that
represents the payload. Each maps to one native owner; no concept is redundant
and no code change is implied. The one distinction learned for no benefit is
"implicit default v6" beside "recommendation v9"; it exists because changing the
default is reserved for the owner. The brief: "Changing the fresh default itself
is the owner's call; propose it with the consequences if it is the right answer,
do not change it silently." Delivering that proposal in the PR satisfies the
Task; the owner's answer is not a precondition, so it does not block.

Proposal carried to the PR (not settled): keep v6 as the implicit default in
this Task. Switching fresh `ObservationConfig()` and `encode_observation`'s
default to v9 would change fresh model architecture, serialized config
identities and the input of every current training recipe that relies on the
fresh default — a training-regime change better made with its own run — while
the explicit recommendation already gives outside consumers a discoverable
answer. Saved versions and omitted-version v1 loading are unaffected either way.

The title's "accepts every legal board" exceeds the brief's done-when; finite
capacities still reject large boards with typed errors. State this in the PR
body rather than widening the Task.
