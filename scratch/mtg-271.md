## Current approach

- `pyproject.toml::project.dependencies` owns public minimums; `scripts/release/prepare.py` preserves them unchanged. `llm` inherits core Torch. Exact runtime groups and `uv.lock` retain reproducible repository environments. Identical Linux/non-Linux Torch markers are necessary for uv's group-specific index selection; the failed alternatives are recorded in `questions.md`.
- `manabot/experiment/execution.py::ExperimentExecution.report` generates notebooks during ordinary execution, so nbformat remains core. Unused direct pandas and its CI prune flag are removed; notebook execution stays optional.
- `.github/workflows/release.yml` builds one sdist and four wheels, then tests each interpreter/platform outside the checkout. `scripts/release/validate.py::validate` compares each wheel's metadata with the source archive and enforces the complete inventory.
- `scripts/release/complete.py::needs_upload` permits only absent publication or an exact inventory/digest match; partial/different publication fails. `complete_github` creates or verifies the tag and notes after PyPI. Only the completion job receives `contents: write`.
- `scripts/play.py::PYTHON_VERSION` owns launcher interpreter/ABI checks. Fresh shared machine setup and active CI use 3.13; frozen experiment setup and supported deployed 3.12 consumers retain their pins.

## Concept review — 2026-11-11

Outcome: nothing to change and no open product choice; advance. The experience
remains one Manabot install with a bundled engine, feature extras, and the
consumer's own dependency lock. Repository runtime groups serve reproducible
development and do not become consumer constraints. The largest former mismatch
was staging rewriting the public dependency contract; source metadata now owns
that contract through the sdist and every wheel. Existing installation docs and
agent guidance already express this experience and need no conceptual rewrite.

Release completion is derived from the retained artifact inventory and both
services, without a separate local completion record. Normal publication ends
with identical PyPI files and a public GitHub entry for the tag and notes. If
PyPI succeeds and GitHub fails, rerun completion using the original artifacts.
If an upload retry finds partial publication or different bytes, it stops for
inspection. Rebuilding the same version is the counterexample to a blind retry:
the version can agree while bytes differ. Preserve the tag, original artifacts,
digests and notes; do not turn recovery into overwrite or automatic repair.

Consumer recovery likewise preserves meaning: resolve an incompatible local
dependency pin or install the missing feature extra in the same environment;
use the wheel matching the interpreter and platform. A local 0.2.0 compatibility
build does not make the historical PyPI 0.2.0 compatible with 3.13. The current
docs distinguish these explicitly. No new execution was performed in this
review; the CI validation above remains outstanding. The review screen
is `scratch/concept-review.html`.
