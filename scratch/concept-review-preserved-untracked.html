The engine scales in its card representation, not yet in its effect vocabulary

The decision I need: whether to stop adding verbs that are shaped like one card, and when. Since T1, Effect has grown in step with the card count. About 45 of its 107 variants serve a single card. Every variant brings its own resolution code, observability rows and an opaque learning token. At tens of thousands of cards, that gives an enum of thousands of variants that the policy cannot generalize across. T6 is about to add faces, Sagas and turn scheduling, which makes it the cheapest point to change the shape.

1 · What the engine is made of

Each card is one Rust value. The engine plays it, the policy reads tokens derived from it, and the observation describes it. Each piece of state below has one owner:

What T6 adds

Faces. CardDefinition.back_face: Option<Box<CardDefinition>>. The face is recorded on the permanent and resets on a zone change. "Return it transformed" enters back face up. characteristics and copiable values start from the current face, so a copy of a transformed Aang copies the back face and cannot transform (CR 712.8, 707.8). Tokens add a reference to the back face's row, the same mechanism token_name uses.

Sagas. CounterKind::Lore, a TriggerCondition::Chapter(n) that fires when lore counters are added, and the CR 714.4 state-based action: sacrifice only once the final chapter has left the stack.

Turn scheduling. An extra-turn queue and pending extra combats on TurnState, with "next upkeep" and "next end step" written as T4 delayed triggers.

Debug engine_tests went 311 s → 157 s → 102 s. The last steps/s figure (≈590 headless) is from July, before any TLA batch.

No performance gate in CI. The Clean-machine Play wait went from 30 s to 120 s to absorb T4. That was more headroom, not a faster engine. No CI check would catch a T6 regression.

Where time goes as boards grow:

  • Any mutable borrow of state clears the characteristics cache, so a rollout recomputes on almost every step. A cloned search world also starts with an empty cache.
  • build_static_index and compute_characteristics each cost about O(permanents × (static sources + effect records)). effects_on is a linear filter called inside per-attachment loops.
  • For each event, trigger scanning snapshots every permanent with abilities and walks the whole object_lki history, which grows over the game.
  • Characteristics owns String/Vec fields, which is about 7% of playout time in allocation.

The total number of defined cards costs nothing per step. Definitions are shared Arcs and the catalog is built once. Cost follows board size, the number of effect records and the length of the game. For card count, that is the right dependency.

3 · Scaling to tens of thousands of cards

Already scales

  • One card representation. The engine, tokens and observation all derive from it.
  • Learning tokens are hashes of rule names, so a new card that reuses existing verbs needs no change to the vocabulary or the model.
  • Open vocabularies (subtypes, counters, effect records) are fact rows, not columns.
  • Per-step cost does not depend on catalog size.

Does not scale yet

  • The effect vocabulary: see below.
  • Counters([i32; N]) is a dense array of every kind on every permanent, and MTG has about 150 counter kinds. It should become a small sparse map.
  • Compile time: tla.rs is 10.6k lines for about 263 cards, roughly 40 lines per card. Ten thousand cards would be about 400k lines in one crate. The card sets should become their own crate.
  • Layers 2, 3 and 5, and dependency order (CR 613.8), are not implemented.
  • Engine predicates shaped like one card, such as CreatureWithNamesakes(8) and Permanent.animated.

The policy sees Effect::SacrificeSource and Effect::SacrificeTriggeringPermanent as unrelated hashes. T6 is about to add "exile this Saga, then return it transformed" (a fourth Exile-and-return), "sacrifice it at your next end step" and "untap all lands you control".

enum ObjectSelector { This, Target(u8), Triggering, Attached, CreatedThisWay,
                      Linked, Each(CardPredicate) }

Effect::PutCounters { on: ObjectSelector, kind: CounterKind, amount: EffectValue }
Effect::Move        { what: ObjectSelector, to: Zone, tapped: bool, face: Face }
Effect::Sacrifice   { what: ObjectSelector, optional: bool }

These three verbs replace about 25 current variants. A token for Move + This + Battlefield means the same thing on every card that uses it. The observability guard and the resolution code shrink accordingly. Hand-written definitions keep their constructor helpers (Effect::sacrifice_this()), so card code stays as readable as it is now.

What has to survive: every directed card test, w17's behavior, and LKI semantics for This after the source leaves play. What changes on purpose: the learning token streams, which means a new content_digest and retraining from w17 checkpoints that read tokens. Counterexample to test it against: a verb whose rules depend on the selector, such as "Return to hand; if you controlled it, draw". If many verbs are like that, the axis is weaker than it looks.

Questions

  1. When should the effect vocabulary move to verbs over an ObjectSelector?
    1. Inside T6: refactor the existing verbs first, then author the 16 cards in the new shape. T6 grows by maybe a week.
    2. As its own Task before T7. T6 writes its new effects in the selector shape where that is cheap and leaves the existing verbs alone. (my recommendation)
    3. Defer until after T7, and keep adding variants for now.
  2. What performance checks should the engine have?
    1. A separate Task: bench_search plus headless steps/s on a fixed workload in CI on a quiet runner, with a budget against a recorded baseline, plus a one-time T4/T5 measurement. (my recommendation)
    2. T6's PR body reports Search-64 and steps/s against main. No gate.
    3. Leave it as it is.
  3. Faces model for T6:
    1. Back face nested in the definition, face state on the permanent, characteristics and copiable values start from the current face. (my recommendation)
    2. Two definitions linked by key, with the permanent switching definition_id when it transforms.
  4. Also file the follow-ups from section 3, sparse counters and a separate card-set crate, as small Tasks? (yes/no)
