One card representation, three consumers

Every card is one Rust value, a CardDefinition, written in its set file. The engine plays it, the learning tokens are a serde walk of it, and the observation describes it. That contract is what already scales: adding a card that reuses existing rules types costs no vocabulary edit, no model change and no per-step work.

// managym/src/state/card.rs (main)

The three things this guide changes

  1. Faces and Sagas enter as data on the types above: a back face is another catalog row, a Saga chapter is a counter-threshold trigger, an extra turn is a queue on TurnState. No new subsystems. Faces, Sagas.
  2. The effect vocabulary gets its missing axis. Today the object a verb acts on is spelled into the verb's name, so Effect grows with the card count (63 → 107 variants over T1–T4). A verb plus an ObjectSelector replaces about 25 variants with 3 and gives the policy tokens that mean the same thing on every card. Effects.
  3. Derived state stops being recomputed on every write. One revision counter invalidates every cache on any mutable borrow. Splitting it by what the layers read, indexing effect records by object, and carrying caches into search clones remove the T3 regression's remaining 15–18%. A CI budget keeps it gone. Performance.

Double-faced cards are two catalog rows and one object

A card's two faces are written together, in one function, so a card is still authored in one place. The pack registers the back face as its own row immediately after the front, so a transformed permanent observes, tokenizes and copies as the face that is showing. The object itself never changes: it keeps its counters, damage, attachments and combat status when it turns over (CR 712.9).

    Copies of a face

    T5 made the copy effect data: Card.copy: Option<CopyEffect { of: CardDefId, exceptions }>, materialized by Game::create_token_copy. Faces fit without a new field: a copy's of is the source's current definition_id, and a copy made from a face that has no back_face of its own cannot transform. That is CR 707.8 and 712.8 falling out of the row model.

Tokens: the front's serialized back_face is a definition reference to the back's row, the same device token_name uses, so the policy reads the back face's own program in place.

    A Saga is a counter kind, a threshold trigger and one state-based action

    Nothing about Sagas needs a new subsystem. Lore is a CounterKind like stun or quest. A chapter is a triggered ability whose condition is "lore counters put on this brought the count to at least N". The sacrifice is a state-based action, so it waits until the final chapter has left the stack (CR 714.4).

      Separate the verb from the object it acts on

      Effect has 107 variants at 657 definitions. About 45 serve one card each. Most of the growth comes from fusing the target into the verb: there are seven ways to put counters on something and nine ways to exile something. Each variant is its own resolution arm, its own observability row and an opaque learning token, so the policy sees SacrificeSource and SacrificeTriggeringPermanent as unrelated words.

      What this buys and what it costs

      • Learning transfer. A Sacrifice + This token pair means the same thing on every card. Today each fused verb is a distinct hash the policy must learn from scratch.
      • Smaller guards. tests/cards/observability.rs matches exhaustively over Effect; it shrinks with the vocabulary, and a new selector is one row rather than N.
      • Cost. New learning-token streams and a new content_digest. Policies that read tokens retrain. Frozen worlds, checkpoints and experiment evidence are untouched; this is a change on the open world.
      • The counterexample to keep. Verbs whose rules depend on which object they hit, such as ReturnToHandDrawIfControlled, do not fold cleanly. Keep them as If { .. } compositions, and measure how many remain. If the fused set does not shrink by at least half, the axis is weaker than it looks.
      decision

      Recommendation: its own Task between T6 and T7. T6 writes new effects (Move … transformed, extra combat, untap-all) in the selector shape where that is cheap and leaves the 107 existing verbs alone, so it stays one cohesive PR. The vocabulary Task then migrates the existing verbs behind constructor helpers, with every directed card test unchanged as the acceptance check.

      What does not need to change

      • ContentPack: a Vec<Arc<CardDefinition>> and a name map scale to 27,000 rows without a design change. Per-step cost never reads the catalog size.
      • Learning tokens: hashed rule names and definition references; a new card that reuses verbs is new rows, not a new vocabulary.
      • The v5 observation: open vocabularies are already fact rows, and the facts block is sized by the board, not the catalog.
      • The observability guard: exhaustive matches that fail to compile when a variant is unencoded. It is the mechanism that keeps the three consumers in parity as the vocabulary moves.
