# MTG-207: render the whole-experiment card page in seconds

Status: implemented, draft (design chosen in-session 2026-10-27; the Task left design open). Speed target not met; see Remaining.

## Outcome (Task directive)

Whole-experiment page (`CardSelection(experiment="mtg183-elemental-eval")`) ≤ 10 s
wall on the converted MTG-183 blocks; u005950 vs heuristic ≤ 3 s; every
filter combination keeps the same per-card values as base 4ab16a140.

## Design

- `card_variants` returns one `CardVariant` per combination: the `CardData`
  summary (`cards=()`) plus `CardColumns`, per-card numpy columns in display
  order. `CardVariant.card_data()` builds records; `card_data` uses it for its
  one selection. The page writes rows straight from columns: no pydantic
  records for 78,741 combinations (12.4M inits in the base profile).
- Per-card sums come from SQL grouped by (combination, card code); cards are
  integer codes in key order, so no per-combination string `np.unique`.
- GIH bootstrap batched by deal count: `estimate`'s weights depend only on n,
  inputs are integer counts (exact sums), so a combination's columns inside a
  shared call equal its own call. Base data has 228 distinct deal counts.

## Delete — do not maintain

- `_card_blocks`, `_CardBlocks`, per-combination `_card_stats`, `_rate`: replaced
  by `_segments`, `_card_totals`, `_gih_estimates`, `_card_columns`. Done.
- `card_variants` returning `CardData`: now returns `CardVariant`; callers
  (page, `card_data`, tests) moved. Done.
- `_Segments` positional `variants/starts/ends` and the `summed_at`/`gih_at`
  index maps: segments are keyed by combination (`at[variant]` slices), and a
  combination without GIH rows reads empty columns instead of a `None` branch.
  Done (compress; `tests/eval/test_card_evaluation.py` 42 passed).

## Measurements

One run each, `/tmp/mtg207/time_save.py` (time_page.py's two selections, saves
the page JSON; no profile repeat). Load average 90–240 on 16 cores throughout,
so wall is inflated; CPU is steadier.

| | u005950 vs heuristic | whole experiment |
|---|---|---|
| base 4ab16a140, etude-sdk 0.2.10 | 3.6 s wall / 4.9 s CPU | 517.2 s / 557.3 s |
| this change, 0.2.10 (the pin) | 2.2 s / 2.4 s | 286.4 s / 266.0 s |
| this change + Etude main `estimate` (#71) | 2.6 s / 2.1 s | 182.7 s / 206.7 s |

Every variant's JSON equals base on both selections (1,452 and 78,741
variants, exact comparison), in both "this change" rows. Whole JSON 254.2 MB.

Where the whole page's cost now sits (Etude main estimate, profiled):
Etude `_percentiles` full `np.sort` over 2,000 replicates × 2.06M card
columns ≈ 115 s of 183 s profiled Python; `estimate` matmuls ≈ 20 s; manabot
Python ≈ 20 s. DuckDB (not in the Python profile) ≈ 55 s CPU / 25 s wall,
mostly the 45.4M-row (combination, card, deal) GIH rollup.

## Remaining (≤ 10 s whole not met)

- Exact equality pins every combination to its own positional bootstrap, so
  the page must resample ≥ 45M card/deal cells × 2,000 replicates and order
  2,000 values for each of 2.06M columns. That alone exceeds 10 s on one
  core. Candidates: an Etude partition-based percentile (only 4 order
  statistics are needed per column); computing combinations on demand
  (needs a server, or a page that no longer embeds every combination); or
  relaxing equality to a shared per-deal bootstrap. The last two change what
  the Task accepts and need Jack Heart's decision.
- Bump etude-sdk to 0.2.11 once published (merged as etude #72, not on PyPI
  at 2026-10-28 03:24Z).
