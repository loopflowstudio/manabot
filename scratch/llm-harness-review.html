One decision. See everything.

Give an untouched LLM a game decision. Get a legal action reference and enough evidence to see how it got there.

Selected for the first demo: one decision with a fully inspectable record. Complete games come later.

1. What you do

Proposed usage: supply observation text and all legal references, invoke selection once, inspect the result. Handwritten inputs are enough for this first demo.

Text + legal references → Harness → Selection record
Decision input
One immutable text prompt and its complete reference list. Apply the model’s own chat template and tokenizer; never truncate silently.
Response attempt
The raw answer, validation error if any, token counts and latency. A repair belongs to the same decision.
Selection record
Chosen reference; origin: initial, retry or fallback; attempts; timing and peak GPU memory. Retain model/tokenizer revisions, template, decoding settings and fallback RNG evidence.

The ownership boundary

MTG-185 runs the model and returns a selection or explicit failure. MTG-184 owns observation representation and binding references to Commands. The caller submits the Command through the native authority. Harness selection itself never advances the game.

Proposed concepts, not implemented APIs. Source: working design, “Data structures and key functions” and “First harness review.”

2. The recovery rule is settled

Accept exactly one listed reference, allowing surrounding whitespace. Commentary, unknown references, multiple references and empty or incomplete answers are invalid.

Legal references: A0, A1, A2

“A1”                 → A1 · initial
“I choose A1” → “A1” → A1 · retry
“I choose A1” → “?”  → seeded uniform draw · fallback

Illustrative paths; not captured model output. Accepted protocol: working design, “Output protocol and recovery.”

Allow one repair, using the unchanged observation and action list plus the failed answer and a protocol-only correction. Both attempts have fixed generation limits within one decision deadline.

Stop with evidence on overflow, runtime failure or deadline exhaustion. Stale bindings and engine rejection also stop the caller’s attempt. None of these permits a fallback or another execution.

Exact repair instruction
Invalid response. Return exactly one action reference from the legal-actions list, with no other text.

Verbatim from the local working draft, “Output protocol and recovery.” No tactical advice.

3. What still needs a decision

Model + runtime
Pick one pinned model and inference runtime. The draft names Qwen3-4B-Instruct-2507 as a candidate; it is not selected or proven to fit.
Limits
Choose context and generation budgets, decoding settings and a decision deadline. Measure complete prompts before freezing the admitted context size.
Execution
Choose where the real-model proof runs. Single-L4 fit is the target; resource allocation remains unselected.

The main interpretation trap

A legal fallback proves the harness can continue; it does not prove the model understood the decision. Report initial validity, repair success and fallback use separately. Later game scores include the whole cohort and describe model plus recovery.

Fine-tuning follows observed interface failures. Training targets, objectives and playing-strength evaluation are separate designs.

4. What would make this review pass

  1. Inspect one real-model decision. Show exact input and token IDs, raw output, selected reference and origin, model settings, token counts, latency and peak GPU memory.
  2. Force the recovery cases. Demonstrate one repair maximum, unchanged input, reproducible legal fallback after two protocol failures, and explicit stopping on runtime failure or timeout.
  3. Measure the operating limit. Show memory and latency at the largest admitted input before claiming single-L4 fit. One short prompt cannot establish it.

Evidence now: a design draft and accepted protocol. The draft records native observation inspection; it contains no real-model or GPU proof. This guide adds no implementation or execution approval.
