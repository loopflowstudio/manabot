# Choices made for review

- **Widths and depth:** Use `w64l2`, `w256l2` (at `BF16_MIN_HIDDEN_DIM`) and `w384l2` (above it), keeping depth (2 layers) and attention heads (4) matched to `baseline.py`. Isolates width without a second depth ladder.
- **Sample count and schedule:** Use seed `25201`, one warmup update followed by three measured complete-game updates (`updates=4`) per live arm while keeping the recipe's 128-update learning schedule. Report per-update spread alongside actual game, decision, retention and optimizer-step counts.
- **Capture reuse:** Use one CPU float32 padded capture per width on the dedicated `mini-heart` checkout, reused across both padded and bucketed parity checks, and run unhooked live `self_play` in isolated fresh subprocesses for throughput.
- **Two-tier parity gate for exploratory `bf16` arms (concept review):** Keep `parity.py` `TOLERANCES` unchanged (`parity.py` still exits 1 on any breach). Require strict parity pass for all float32 arms and hard execution/device/dtype/finiteness pass for all `bf16` arms. Still time finite, verified-dtype `bf16` arms that fail only `TOLERANCES["bfloat16"]` (e.g. near-zero-loss relative error already observed at w64l2), badging them `approximate (parity FAIL)` beside their failed components and separating them from strict-admitted winners (matching `mps_retest.md`). Passed over: strict binary blocking of all `bf16` tolerance misses, which risks leaving all 12 `bf16` cells empty. Reversible without re-running because parity and timing receipts are stored independently.
- **Explicit `threads=4` and sub-phase attribution (concept review):** Set `SelfPlay.threads = 4` across all arms (M1's 4 performance cores, `SelfPlay`'s validated ceiling `le=4`) instead of silently inheriting `baseline.py`'s `threads=1` default, and surface existing `self_play.step` sub-phase timers (policy-only collection rate, Rust engine share, learning targets vs minibatch split) from Etude logs with zero extra hooks. Passed over: leaving `threads=1` (throttles CPU to 1 core against the 8-core M1 GPU) or reporting only opaque top-level totals.
- **Keep `resolve("torch")` unchanged (concept review):** Pass explicit `device`, `precision`, and `bucketed_shapes` through `ParityBackend.load` and `parity.check` (plus strict precision validation in Torch `Learner`/`forward_precision`) rather than changing `resolve("torch", precision=...)`'s existing contract tested in `tests/test_package_boundaries.py`.
- Observe the scalar critic head's actual output dtype during parity. Both frameworks promote logits internally, and MLX promotes public critic values as well. The ordinary MLX forward now applies that last cast after the shared head computation. Torch CPU refusal moves the autocast integration fixture onto supported hardware with a one-seat exact quota.
- Give each width a fresh output directory and each worker a 30-minute elapsed-time limit. The mini measured all widths from the same pinned runner. The offline reader additionally checks Etude's recorded seed, width, layout, device and precision.
- Retain parity/live receipts, Etude tracking rows and the three captures under `experiments/data/mini_baseline_backends/`; leave each cell's `training/` checkpoints (about 7 GiB) on mini-heart. The report reads only receipts, and the captures reproduce parity.
