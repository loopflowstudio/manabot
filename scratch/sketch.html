Part 1. Etude's "Training" page

Training

You write a file with a train function in it. Etude runs that function on a machine, and runs it again on another when the first is taken away. Everything it records is files in a directory or bucket you own.

None of the calls below does anything you could not write yourself in an afternoon. They are worth using because the rest of Etude reads what they write: the launcher, evaluations, reports and other runs.

One function, one config

# train.py
from pydantic import BaseModel

class TrainConfig(BaseModel):     # yours: any fields you like; no seed, see below
    lr: float = 3e-4
    updates: int = 1000

def train(config: TrainConfig) -> None: ...

The config is your own class. Etude asks three things of it and of train: built

  • The config is a Pydantic model. There is no Etude base class and no required field.
  • It survives a trip through JSON, because that is how it reaches the machine. Numbers, strings, lists and nested models are fine; an open file or a function is not. Etude checks this when you launch and refuses there, not on the rented machine.
  • train takes that one parameter, annotated with the config's type, and sits at the top level of a file your project can import.

Calling train is one attempt at the whole job. Calling it again with the same config, on the same run, carries on from what the last attempt saved. It ends in one of three ways: built

ItMeansEtude then
returnsthe job is finishedmarks the run finished
raises Stoppedit saved and left on purposecalls it again, here or on another machine, inside the run's limits
raises anything elseit failedmarks the run failed

Jobs and runs

Two words, used strictly. A job is what to run: your function and its config, with no seed. A run is a job with a seed: the thing that is launched, named, carried on and reported. built

# job.py: you declare jobs
def runs() -> list[Run]:
    job = training(train, config=TrainConfig(), max_hours=2, max_usd=Decimal(4))
    return job.runs(0, 1, 2)          # three runs of one job

So the seed is not a config field. The config says what the experiment is; the seed says which repetition this is. Inside train you read it from the run: proposed (today the launcher passes it as ETUDE_SEED, and Manabot keeps a seed in its config)

with track(clocks=[...], config=config) as run:
    torch.manual_seed(run.seed)

Everything in the rest of this page is about a run. Carrying on means the same run: the same job and the same seed.

The run

with track(clocks=[Step("updates", "optimizer updates")], config=config) as run:
    ...

track opens the run. A clock is an x-axis you declare once, with a line saying what it counts. Every row and every checkpoint is placed on every declared clock. Declare a second clock, such as Time("training_seconds", ...), when one is not enough. built

Naming, open: track now also saves state, publishes checkpoints and answers "should I stop". Your words: "tracking doesnt clearly say like 'save logs, and checkpoints, ...'". See the last question.

Counting

target = int(run.until("updates", default=config.updates))
for update in run.steps("updates", start=state.update, until=target):
    ...

run.until is how far to go: your default, unless the launch asked for another target (etude continue --until updates=6400). built

run.steps yields start + 1 up to until. Inside the loop, rows and checkpoints are placed on that clock for you. When the machine's time is nearly up or someone asks the run to stop, the current pass finishes and the next raises Stopped. Code after the loop runs only when the target was reached. proposed

Carrying on

Every run can be carried on. You tell Etude which objects hold what you have learned; it saves them, moves them to the next machine and loads them back. proposed

model, optimizer = build(config)
at = run.resume(model=model, optimizer=optimizer)   # loads the last save into them; where each clock stood, or zeros
for update in run.steps("updates", start=at["updates"], until=target):
    ...
    run.save()                                       # Etude decides when it is due; always before a stop

Anything with state_dict() and load_state_dict() works: PyTorch modules and optimizers as they are. A few numbers of your own ride along as a Pydantic model: run.resume(..., extra=Counts()).

What is on disk is ordinary and needs no Etude to read:

out/state/
  state.json       {"at": {"updates": 400}, "seed": 197, "commit": "8773d51", "extra": {...}}
  model.pt         torch.save(model.state_dict())
  optimizer.pt

Keeping your code compatible between attempts of one run is yours. Etude checks that the config and seed match; it does not check that your model, your file format or your environment are the same, and changing them mid-run is undefined.

Carrying on means from the last save, with the same weights and optimizer. It does not restore random streams or games in flight unless you keep them in an object you pass.

If your state is not shaped like this, write it yourself: run.save(lambda folder: ...) hands you an empty folder, and run.resume() hands the last one back. Or ignore all of it and use run.out, a directory that follows the run. built (run.out)

Rows

run.log({"loss": 0.42, "entropy": 1.3})
run.log_table("games", rows)

A row is a dictionary of numbers. A table is many rows that belong to one point in training, such as the outcome of every game since the last update. Outside run.steps, or for a second clock, pass the clocks yourself: run.log(row, updates=400, training_seconds=912.5). built; filling the stepped clock in is proposed

Checkpoints

run.checkpoint(path)

A checkpoint is a model someone else will use: an evaluation seats it as a player, another run starts from it. It is recorded with where every clock stood, and it never changes. Recording the same file at the same point twice is harmless. built

State and checkpoints are different things. State is for you, is replaced each save, and holds optimizers and counters. A checkpoint is for others, is kept, and holds what plays.

Several models

Many loops train more than one model: a policy and a value model, a drafter and a deck builder and a player. A checkpoint is then a folder, written the same way state is: you get an empty folder, write your files, and return a record that names them. proposed

class Player(BaseModel):                 # becomes checkpoint.json
    models: dict[str, str]               # "drafter" -> "drafter.pt"

def export_player(models: dict[str, nn.Module], folder: Path) -> Player:
    for name, module in models.items():
        torch.save(module.state_dict(), folder / f"{name}.pt")
    return Player(models={name: f"{name}.pt" for name in models})

Part 2. The hard case: Jace

Parts 2 and 3 still show the earlier form (a Saved class with export and restore). Under "Carrying on" above, Jace would pass its five models and six optimizers to run.resume, and Manabot its learner, optimizer and EMA with extra=Counts.

Jace (RyanSaxe/jace) learns to draft, build decks and play. One iteration drafts pods, builds a deck from every pool, plays the decks, and updates five models through six optimizers. Opponents and the other draft seats can be past versions. A schedule turns dials by iteration: the drafter is frozen for the first 2,000. It carries its own tracking.py to record all this.

What is checked: in PR #103 a checkpoint is one file, and a different file recorded at the same point becomes an unnamed second version (updates-400.ordinal-2). So today Jace's six models at one iteration would be six versions that nothing tells apart. That is what "Several models" above is for.

jace/loops/run_limited.py proposed; limited_iteration, phased_schedule and model_drafter are Jace's own, unchanged

class LimitedConfig(BaseModel):
    seed: int = 0
    iterations: int = 40_000
    drafter_starts: int = 2_000
    pull_ends: int = 10_000
    past_seats: int = 2               # draft seats filled by earlier versions
    checkpoint_every: int = 500


class Saved(BaseModel):               # state.json
    iteration: int
    models: dict[str, str]
    optimizers: dict[str, str]


class Player(BaseModel):              # checkpoint.json
    models: dict[str, str]


def train(config: LimitedConfig) -> None:
    with track(clocks=[Step("iterations", "draft, build, play, learn rounds")], seed=config.seed, config=config) as run:
        setup, learners = build(config)                         # fresh models and optimizers
        found = run.load(Saved)
        iteration = restore(found, learners) if found else 0    # loads weights and optimizers in place
        schedule = phased_schedule(drafter_starts=config.drafter_starts, pull_ends=config.pull_ends)
        target = int(run.until("iterations", default=config.iterations))

        for iteration in run.steps("iterations", start=iteration, until=target):
            rng = random.Random(f"{config.seed}-{iteration}")

            # Who else is at the table: earlier versions of this run, when there are any.
            past = run.checkpoints()
            seats = rng.sample(past, k=min(config.past_seats, len(past)))
            other_seats = [model_drafter(load_drafter(c.folder), generator=generator(rng)) for c in seats]
            rival = rng.choice(past) if past else None
            opponent = load_policy(rival.folder) if rival else learners.policy

            metrics = limited_iteration(
                setup, learners,
                dials=schedule(iteration),
                opponent=opponent, other_seats=other_seats,
                start=start_games, rng=rng,
            )

            run.log(metrics)                                    # "player/loss", "drafter/loss", ...
            run.log_table("trained_against", [
                *({"role": "draft seat", "iterations": c.at["iterations"]} for c in seats),
                *([{"role": "opponent", "iterations": rival.at["iterations"]}] if rival else []),
            ])
            run.save(lambda folder: export_state(learners, iteration, folder), every=25)
            if iteration % config.checkpoint_every == 0 or iteration == target:
                run.checkpoint(lambda folder: export_player(modules(learners), folder))

The state

Today load_state and save_state pickle one dictionary into state.pt, write a temporary file and rename it, and compare settings field by field (lines 407–498). In the sketch the record is JSON, the tensors are two files, and the atomic write and the settings refusal are Etude's.

manabot/training/loops/self_play.py

class Saved(BaseModel):
    """What `state.json` holds; the tensors are the files it names."""

    format: Literal["manabot.self-play-state/v2"] = "manabot.self-play-state/v2"
    world: str
    seed: int
    source_commit: str
    update: int
    counts: Counts
    learner: str = "learner.pt"      # raw weights and Adam
    ema: str | None = None


def export(state: LoopState, folder: Path) -> Saved:
    """Write the learner's tensors into `folder` and return their record."""
    torch.save(
        {"raw": state.learner.agent.state_dict(), "optimizer": state.learner.optimizer.state_dict()},
        folder / "learner.pt",
    )
    if state.ema is not None:
        torch.save(state.ema.state_dict(), folder / "ema.pt")
    return Saved(
        world=state.settings.world,
        seed=state.seed,
        source_commit=checkpoint_source()["commit"],
        update=state.update,
        counts=state.counts,
        ema=None if state.ema is None else "ema.pt",
    )


def restore(saved: Saved, folder: Path, settings: SelfPlay) -> LoopState:
    """The learner `export` wrote. Etude has already refused another config or seed."""
    if saved.world != settings.world:
        raise StateMismatch(f"state was written for world {saved.world!r}, not {settings.world!r}")
    space = ObservationSpace(settings.observation)
    learner = create_learner(settings, create_model(settings, space))
    tensors = torch.load(folder / saved.learner, map_location="cpu")
    learner.agent.load_state_dict(tensors["raw"])
    learner.optimizer.load_state_dict(tensors["optimizer"])
    ema = None
    if saved.ema is not None:
        ema = deepcopy(learner.agent)
        ema.load_state_dict(torch.load(folder / saved.ema, map_location="cpu"))
    return LoopState(settings, saved.seed, space, learner, ema, update=saved.update, counts=saved.counts)

Counts would become a Pydantic model so it sits inside Saved. The world check stays in Manabot because a world is not a config field Etude can see.

The loop

Today's self_play is 86 lines (754–839). It takes an output path and an optional tracker, creates the directory, handles three resume cases by hand, checks run.stopping(), saves in three places and raises Stopped.

def self_play(settings: SelfPlay, run: Run, *, seed: int, updates: int) -> Path:
    """Train to the run's update target and return the final policy's path.

    Call it again on the same run to carry on. Only the learner is durable:
    each attempt starts fresh random streams.
    """
    with device_settings(settings):
        found = run.load(Saved)
        state = restore(*found, settings) if found else new_state(settings, seed)
        target = int(run.until("updates", default=updates))
        rng = np.random.default_rng(seed + MINIBATCH_SEED + state.update)
        with self_play_games(settings, run.out, seed=seed, start=state.update) as collector:
            seed_random(seed + state.update)
            base = state.counts
            if is_checkpoint(settings, state.update) or state.update >= target:
                policy = publish(run, state)         # update 0, or a milestone whose attempt was lost
            for update in run.steps("updates", start=state.update, until=target):
                state, row = step(state, collector, rng, base=base, out=run.out)
                seconds = state.counts.training_seconds
                run.log(row, training_seconds=seconds)
                run.log_table(OUTCOME_TABLE, collector.stats.self_play.drain(), training_seconds=seconds)
                milestone = is_checkpoint(settings, update) or update == target
                run.save(lambda folder: export(state, folder), every=settings.save_every, now=milestone)
                if milestone:
                    policy = publish(run, state)     # state first, then the immutable policy
    return policy


def publish(run: Run, state: LoopState) -> Path:
    path = write_policy(run.out / "checkpoints", state)
    run.checkpoint(path, updates=state.update, training_seconds=state.counts.training_seconds)
    return path

A recipe with phases

The belief recipe trains a policy, collects its histories, then fits a sampler. This is the case that decided how run.steps ends. If a stopped loop simply fell out of its for, the next phase would run on a half-trained policy. Because the next pass raises Stopped, the lines after self_play run only when the policy reached its target.

Seven lines are Etude's (track, load, until, steps, log, save, checkpoint), plus an export and restore of about ten lines each. This is roughly what the front page's training sample would be.

Part 4. Stages: train A, then train B

"the end state may be allowing experiments to have like a full DAG of training stages, each of may have multiple runs, and each run having possibly multiple trained models, but the heavy heavy default should be 1 stage 1 model, and the API should accept that but generalize where needed"

Stages reuse the shape eval(state) already has: a function of what exists that returns what is wanted. etude launch starts whatever is wanted and not yet run, so running it again after the first stage finishes starts the second.

def runs(state: ExperimentState) -> list[Job]:
    jobs = [training(imitate, config=ImitateConfig(), name="imitate", max_usd=Decimal(5))]
    first = state.finished("imitate")
    if first:
        jobs += [
            training(self_play, config=SelfPlayConfig(seed=seed), name=f"self-play-{seed}",
                     start=first.final, max_usd=Decimal(20))
            for seed in range(3)
        ]
    return jobs

That is a DAG with no new noun. The edges are the start= arguments; a stage with three seeds is three jobs; an experiment is still a label over its runs. What Etude adds, and what an agent-written tracker would not have for free:

  • the later job is given the exact bytes, checked by digest, on whatever machine it lands on;
  • the link is recorded, so a report or the league can say which imitation run a self-play checkpoint descends from;
  • each stage has its own budget and machine shape (imitation wants a GPU; self-play wants cores).

Built in PR #103 and reused here: a job's Input (a file from another run's folder, digest-checked, delivered before start), continue_from (a new run seeded from a parent, with the lineage recorded), and ExperimentState with state.run(name). Proposed: runs(state), start=, state.finished, run.input. OpenAI Five's surgery is the built continue_from(..., config=changed); I have not checked what it refuses.

One run or two?

Phases stay inside one run (rung 3) when they are cheap, always run together and nobody evaluates the middle. They become separate runs (rung 4) when any of these holds: the stages want different machines or budgets; several later runs start from one earlier run; the earlier result is evaluated or reused on its own. Manabot's belief recipe is rung 3 today and would be rung 4 by the third test, since the policy it trains is evaluated on its own.
